# 新旧版本兼容

目标：用户不用同时升级两端，新版本和老版本照常互通；强制升级只作为最后手段。

## 规则

1. **新功能用能力位协商，不升版本号。** 握手里双方交换 `Caps`（`crates/core/src/proto.rs`），
   被控端回 `Accept` 时给出交集。交集里没有的功能就不开，界面上置灰并说明“对方版本不支持，升级后可用”。
   - 第 0–15 位是编解码能力，第 16 位起是功能能力（剪贴板 16、声音 17……）。位置一经发布不能改。
2. **只在末尾追加字段。** 握手消息（Hello、Accept）和所有信令消息，解码时读完认识的字段就停，
   后面的字节忽略。已有字段不能改类型、顺序和含义。
3. **没协商过的消息不发。** 老版本读到不认识的控制消息会结束会话；不认识的数据报通道、流类型会被丢弃，
   不影响会话。新消息只在对方声明了对应能力位后才发。
4. **版本号只为无法兼容的改动而升。** 被控端接受 `MIN_VERSION` 及以上的所有版本（包括比自己新的），
   低于 `MIN_VERSION` 才拒绝并提示升级（`RejectReason::Version`）。
5. **服务器向后兼容客户端。** 新服务器要能服务老客户端；新客户端连老服务器时，老服务器不认识的请求会关掉
   信令流，客户端要当作“服务器不支持”处理并退回老办法（例如问不到集群节点列表就用缓存）。

## 怎么保证

- `crates/core/tests/compat.rs` 冻结了握手、信令、数据报包头的字节，并检查“追加扩展字段后老格式仍能读”。
  改坏了老格式 CI 就失败。**不要为了让测试通过去改那些常量。**
- 加新功能时在同一个文件里补一条：对方能力位里没有这个功能时，会话照常建立、功能关闭。

## 升级提示（计划）

客户端启动时查询最新版本：有新版本时提示（不打断使用）；只有本机版本低于 `MIN_VERSION`、
连不上新版本的对端时，才提示必须升级。

## 历史

- 2026-11 之前的测试版协议改过多次，没有兼容；从协议版本 1 + 本规则起开始保证兼容。
