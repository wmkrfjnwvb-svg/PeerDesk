# 用户实测：Mac 被控（2880×1800、Wi-Fi），Windows 控制，2026-11-27

产品负责人实测，版本 dev `7a7e3be`：码率控制状态机第 0–3a 步合进去之后的第一个安装包。
日志已经用 `scripts/anonymize-log.py` 脱敏：IP、设备编号、设备码、用户目录都换成了占位符，其余原样保留。

## 文件

| 文件 | 内容 |
| --- | --- |
| `host-mac.log.gz` | 被控端（Mac）完整日志，脱敏 |
| `controller-win.log.gz` | 控制端（Windows）完整日志，脱敏 |
| `per-second.csv` | 从被控端日志抽出的每秒一行：帧数、画面和线上码率、目标码率、帧率上限、编码耗时、在途、丢失、重传、往返、纠错、画像；最近一份反馈的排队、延迟趋势、丢包、送达、包串测速；当时的码率状态。用 `scripts/log-to-trace.py` 生成 |
| `decisions.csv` | 发送端每一条“决定”：码率状态切换（带原因）、升降码率、探测和结论、帧率 |

日志里的时间是 UTC，产品负责人说的是北京时间（UTC+8）。两次会话：第 1 次 01:48–01:54，第 2 次 01:54–02:34（UTC）。

## 产品负责人的感受（北京时间）

- 9:55–9:56：从静止恢复时有半秒到 1 秒的卡，“没啥大问题，还是很丝滑，不影响使用”
- 10:00、10:03：从静止恢复，很快，没问题
- 10:04–10:05：网络变差，但还是很丝滑
- 10:12、10:17、10:34：没问题
- 总评：“目前是最好的版本，操作丝滑，没卡顿，界面基本没模糊”，“码率和帧率不乱”

## 数据里看到的（第 2 次会话，2426 秒）

- 往返中位 35 ms，95% 分位 50 ms，最大 467 ms（Wi-Fi 延迟尖峰）；目标码率中位 10.3 Mbps。
- **9:55:56 那一下**（01:55:56 UTC）：
  - 静止后画面一动，第一帧用掉了预算的八成以上，状态从“应用受限”切回“跟踪”；
  - 同一份反馈里排队 16 ms、送达 81 kbps（还是静止时的送达），跟踪规则按“送达 × 0.85”把码率从 15.9 Mbps 降到底线 100 kbps；
  - 同一秒包串测速拉回 6.2 Mbps，下一秒核实探测证实 13.3 Mbps。
- 整个日志：降码率 596 次，其中 374 次是“发送端没用满码率”时降的，259 次降到 1 Mbps 以下，大多一两秒内被包串测速或核实拉回。
  10:05 前后（02:05 UTC）最密。
- 核实探测 52 轮：证实 32、否定 3、中止 17（又开始发帧），每轮都有结论。

## 怎么用

- **回放场景**：用 `per-second.csv` 的帧数、码率起伏做“真实用户的操作节奏”，用往返、排队的分布校准仿真里的 Wi-Fi 毛病。
- **回归用例**：9:55:56 这种“刚从应用受限切回跟踪，按静止时的送达速率降码率”的情况，修的时候在仿真里复现，修完对比。
  见研究总表待办里的“跟踪状态下没用满码率时按送达速率降码率”。
