## 0. 目标和闭环验收

核心用户：在 Mac mini、Windows、Linux 上常驻跑 AI Agent 的个人和独立开发者。他们最痛的是**人不在机器前，出了问题修不好**。
付钱的理由是我们替他们盯着机器、出事马上告诉他们、能从手机上修好；留下来的理由是不远程的日子里也一直在提供价值（健康面板和提醒）。

**第一阶段的闭环验收**（真机，产品负责人亲手做一遍；能自动的部分进集成测试）：
1. 一台新装的 Mac mini 装上 PeerDesk，用邮箱验证码登录（或在手机上批准审批码），进入账户。
2. 体检向导逐项检查，给出原因和修法；按提示修完，全部变绿。
3. 手机（加到主屏幕的网页版）上看到这台 Mac mini：在线、各项权限齐、无人值守已开。
4. 拔掉 Mac mini 的网线：设定的时间内手机收到“离线”推送，打开看到原因（最后在线时刻、上次的状态）；插回去，收到“回来了”，列表变绿。
5. 重启 Mac mini：如果设置正确，它自己回来，手机上不报警（在阈值内回来的只记日志）；如果 FileVault 把它卡在开机界面，到时没回来，推送里说明“可能卡在开机密码界面”，给出修法。
6. 屏幕录制权限被收回（模拟更新后失效）：手机收到“权限失效”提醒，写明哪一项、怎么修。
7. 免费档加第 3 台设备时，清楚提示上限和升级办法；在 Stripe 沙盒付款升级后，马上能加。
8. 在 Claude Code 里问“我有哪些电脑在线、状态怎样”，本机 MCP 答得出来。

iOS 原生 App 出来以后（并行线，第 3 节）再加一条：点推送直接进入那台设备的画面，接管。

## 1. 谁存什么、谁做什么

| 部分 | 存什么 / 做什么 | 说明 |
|---|---|---|
| Supabase（托管云） | 用户（Auth）、`plans`、`billing_customers`、`subscriptions`、`stripe_events` | 登录和授权都在这里；RLS 全开，客户端只能读自己的订阅 |
| Cloudflare Worker（Rust，`workers-rs`） | 建 Checkout 和 Portal 会话、收 Stripe webhook、写订阅表、把档位写进用户的 `app_metadata` | 胶水代码。Stripe 密钥和 Supabase secret 密钥只在这里，不上中继节点。权益判断调 `core` 的纯函数 |
| `peerdesk-server` | 账户设备表、在线状态、设备自报的健康、提醒规则和发送、给网页和客户端的账户接口 | 只校验 Supabase 令牌（JWKS，ES256），不持有 Supabase secret 密钥。自托管不配 Supabase 时用本地账户（`AccountAuth` 的另一个实现），表结构一样 |
| 桌面客户端 `peerdesk` | 登录、令牌存钥匙串、自报健康、体检和修复向导、设备列表、本机 MCP | 一个进程专管刷新令牌 |
| 网页版（`web/`，手机优先） | 登录、设备健康列表（实时）、提醒设置、订阅管理入口；加到主屏幕后收网页推送 | 现有 React 控制台旁边加用户页面。网页推送用 VAPID（RFC 8292），自托管服务器可以自己生成密钥，不依赖我们 |
| iOS App（并行线） | 设备列表、接管画面、APNs 推送、IAP | SwiftUI + Rust 核心，见 iOS 方案报告 |

**权益怎么到服务端**：
- Worker 收到订阅变化后，把 `{plan, devices, relay_gb, until}` 写进该用户的 `app_metadata`，于是用户的访问令牌里就带着档位。
- 服务端在账户级操作（入表、订阅设备列表）时读令牌里的档位，并按账户缓存，带到期时间。
- 被控端日常登记不带令牌，用缓存的档位。缓存过期、又没有新令牌时，按最近一次的档位继续服务，宽限 7 天，并在日志和界面上说明。
- 第 P8 步实现时再核实：`app_metadata` 写入后要多久出现在新令牌里；令牌刷新前的滞后（最多 1 小时）对“付完钱马上能加设备”的影响。客户端付款回来后强制刷新一次令牌。

## 2. 分步（每步能单独合进 dev，带验收）

工作量是一名熟悉代码的工程师的推断。传输无关的步骤不跑 144 次测量；改了 `core`、`net`、`server` 会触发端到端任务；覆盖率 99% 不降。

| 步 | 做什么 | 验收（做完能演示什么、测试断言什么） | 依赖 | 工作量 |
|---|---|---|---|---|
| P1 | **收尾账户设备表**（`devices` 分支 S1a–S1d）。先改两处：账户号改成 16 字节（托管云是 Supabase 的用户 UUID，自托管是现有 8 字节号补齐）；入表令牌按调研改成绑定账户、默认一次性、1 小时有效，批量部署时显式选“可复用” | N-devices S1 的全部测试；三台真实二进制入同一账户，`peerdesk devices` 列出三台；非成员 0 次读到别的账户 | 无 | 3–4 天 |
| P2 | **登录**：服务端 `AccountAuth`（`SupabaseJwks` 和 `Local`）；桌面 `peerdesk login`（邮箱验证码）；刷新令牌存钥匙串，钥匙串不可用时明确报错；无屏幕主机的审批码流程（`/enroll/start`、轮询、网页 `/activate` 批准，主机上不存 Supabase 令牌） | 用自己生成的 ES256 密钥和假 JWKS 服务，覆盖调研 8.2 的所有失败情形（错 `iss`、`aud`、过期、`HS256`、`none`、不认识的 `kid`、匿名和 `service_role` 令牌、JWKS 取不到、轮换中新旧并存）；审批码：限频、过期、拒绝、批准各一条集成测试。对真实 Supabase 测试项目的集成测试手动跑一次，结果写回本文 | P1；真实项目要你建 | 5–6 天 |
| P3 | **在线状态订阅推送**（N-devices S2）：`Watch`、`DeviceEvent`、`PresenceHub` 纯逻辑；客户端 `Watcher` | N-devices 第 8 节的门槛：正常下线 p95 < 1 秒、掉线 ≤ 空闲超时 + 1 秒、300 台 10 个订阅者 60 秒随机上下线后 100% 一致 | P1 | 4–5 天 |

## 3. 并行线：iOS 原生 App

照 iOS 方案报告的阶段走，这里只写第一阶段内要做到的部分：
- **iOS P0**：Rust 核心编到 `aarch64-apple-ios`，SwiftUI 壳，用 `AVSampleBufferDisplayLayer` 在真机上显示一路真实主机的真实画面（不用合成画面）。验收：TestFlight 内部构建，在你的 iPhone 上连上一台真实主机，首帧时间、连续解码帧数、冻结次数写进诊断页并导出。
- 新增提交标记 `[ios]`（只在 macOS 机器上编 iOS 并跑模拟器），写进 CLAUDE.md 的 CI 表时一起加。
- 要你准备：一台能跑 Xcode 的 Mac（Mac mini 可兼用）、一台 iPhone、苹果开发者账号。没有 Mac 也能做，但每次改动要走 CI 加 TestFlight，一次循环几十分钟。

iOS 版的推送用 APNs。APNs 的密钥属于我们的开发者团队，自托管服务器只能通过托管云的推送转发发 iOS 推送（只带令牌和固定文案）；自托管用户在网页版上可以用自己的 VAPID 密钥收推送，不依赖我们。

## 7. 风险和没核实的

1. **macOS 对一部分安全弹窗不接受程序模拟的点击**（防止恶意软件给自己授权）。远程点“允许”能对付哪些弹窗（屏幕录制、辅助功能、各类授权框、Agent 自己的确认框），要在真 Mac 上逐个试。这决定“手机上一点就过”能承诺到哪一步。结果写回本文，点不了的在界面上写明要到机器前操作。
2. **没接显示器的 Mac mini 屏幕采集给不给画面、给多大**：两份资料说法相反，要实测，决定虚拟显示器排第几。
3. **iOS 上网页推送要先“加到主屏幕”**（iOS 16.4 起），多一步操作；页面上要有清楚的引导。安卓和桌面浏览器不用。
4. **`web-push` crate**（0.11.0，Apache-2.0）的加密后端和依赖没核实；如果要拉进 OpenSSL、影响静态构建，就用 RustCrypto 自己写 RFC 8291 的加密（约 200 行）。
5. **Supabase 回环地址任意端口**能不能进重定向白名单没核实（调研第 9 节）；桌面先用邮箱验证码，不依赖它。
6. **`workers-rs`**（0.9.0，Apache-2.0，Cloudflare 官方仓库）成熟度没核实；P8 第一天先做一个最小 webhook 验签的 Worker 试通。
7. **权益的滞后**：`app_metadata` 改了以后，旧令牌最多 1 小时后才刷新；付款回来强制刷新一次令牌，服务端在入表时以令牌为准。实际滞后在 P8 实测。
