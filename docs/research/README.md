## 0. 起因：为什么要重新调研

本机实测时画面模糊、刷新慢、像老机器一样一屏一屏刷新。原因已经定位：

- 自研的块编码对真实桌面（壁纸、图片、抗锯齿文字）几乎压不动：1080p 第一帧 3.9 MB，默认码率下 10 秒以上才清晰，补清晰时一片片刷过去。
- 起步码率固定 4 Mbps，本机和局域网的带宽没有被探测出来。

同一张画面用 H.264（OpenH264）实测：第一帧 143–174 KB，静止时每帧十几到几十字节，打字时每帧约 50 字节，软件编码 1080p 每帧约 14 ms。

## 1. 远程桌面和视频通话的本质区别

这是整套设计的出发点，也是 PeerDesk 和基于 WebRTC 的产品拉开差距的地方。

| | 视频通话（WebRTC 的设计目标） | 远程桌面 |
| --- | --- | --- |
| 流量形态 | 持续、平稳 | 大部分时间静止（几乎零流量），突然爆发（切窗口、滚动） |
| 内容 | 自然图像，人脸 | 文字和界面为主，夹杂视频和照片 |
| 什么最重要 | 声音连续、画面流畅 | 操作跟手（输入到显示的延迟），文字清晰 |
| 能容忍什么 | 画面略模糊 | 短暂模糊可以，卡住不行；静止后必须清晰 |

两个直接后果：

- WebRTC 的 GCC 和 BBR 都在“一直在发”的假设下估计带宽。屏幕静止时估计值停住、过期，突然来一个大画面就估不准。见报告 A。
- 没有找到专门研究“长时间空闲、突然爆发”这种流量的论文。这块是 PeerDesk 可以做出原创性的地方。

## 2. 视频编码（决定：主力改用视频编码）

- **格式**：硬件编码优先，按 AV1 > HEVC > H.264 选双方都支持的；没有硬件时用 OpenH264。
  - 发布版在运行时下载 Cisco 官方的 OpenH264 二进制并校验，以符合它的专利授权条件。
  - 开发和 CI 时从源码编译。
- **编码器听传输层指挥**：
  - 每帧给字节预算，不自己猜码率。
  - 丢包时从“长期参考帧”恢复，不发关键帧；不支持的编码器才退回关键帧。
- **长期参考帧要先做冒烟测试**：建编码器时先测它是否真照做。Airhand 发现 NVIDIA 的 HEVC 和 Intel 的 AV1 报告“已照做”但实际没有。
- **静止后补清晰**：画面停下约 200 ms 后，把最后一帧再编几次（只补残差，最多约 8 帧），然后停发。这解决了“先糊、过一会整屏刷新”的问题。
- **文字清晰度，后续做**：
  - RDP 的 AVC444：用两路 4:2:0 拼成 4:4:4，任何硬件解码器都能用。
  - 原生 4:4:4。
  - 目前没有硬件能编码 AV1 4:4:4。
- **块编码**：保留在仿真里做对照，不再作为主力。

## 3. 传输算法（核心，自己写）

### 3.1 结构

- 画面走 QUIC 数据报，码率、发送节奏、重传、前向纠错（FEC）全由 PeerDesk 自己的代码控制。
  - 原因：quinn 自带的拥塞控制只能看到确认字节、往返时间和丢包，看不到接收时间戳和帧边界，只能输出一个窗口值（报告 A 核对过源码）。
  - quinn 的拥塞控制只当最后一道安全网。
- **对照组**：Airhand 的“每帧一条 QUIC 流、重传交给 QUIC”实现成本低，做成另一种模式，在同一套端到端测试里比较，用数据决定。

### 3.2 带宽估计

几种信号合起来用，任何一个报“过载”就立即降码率：

1. **每帧测“链路有多满”**（借鉴 Pudica，NSDI 2024，用于云游戏）：每一帧本身就是一次探测，不需要额外的探测包。
2. **大帧当免费探测**：一帧拆成的多个包连续到达，用它们的到达间隔估计瓶颈带宽。
3. **延迟上升趋势做早期报警**（借鉴 WebRTC 的 trendline）：排队刚开始形成就察觉，不等丢包。
4. **丢包**：区分随机丢包和拥塞丢包。随机丢包靠纠错补，不降码率。

### 3.3 每帧预算与发送

- 每帧预算 = 码率 ×（截止时间 − 当前排队延迟）− 在途字节。截止时间先取 50 ms，后续用测试校准。
- 发送队列最多放一帧，新帧直接替换旧帧：网络慢时跳到最新画面，不积压。
- 发送节奏：按估计带宽的 1.1–2 倍成组发出（受控突发），既不一次全部发出，也不过度平滑。

### 3.4 空闲与爆发（远程桌面特有）

- 空闲时冻结带宽估计，并逐渐降低对它的信任度。每 250–500 ms 发一个很小的保活包，维持往返时间测量和 NAT 映射。
- 用户一开始操作（键盘、鼠标）就先探测带宽，因为大画面变化很可能马上到来。
- 估计值不可信时，大画面先用较低画质发出，随后几帧内补清（第 2 节的补清晰机制）。

### 3.5 丢包恢复

- 截止时间内能补上的，用重传（NACK）补。
- 长往返、高丢包的链路，按预测调整纠错包比例。参考值：Sunshine 默认 20% Reed-Solomon，GeForce Experience 主机在 4K 下降到 5%。
- 补不上就放弃这一帧，从长期参考帧恢复。

### 3.6 接收端与抗抖动

- 桌面操作不加缓冲：新帧解完，在下一次屏幕刷新时显示。
- 只有播放视频的区域加一个很小的抖动缓冲，让播放平稳。

### 3.7 无卡顿切换清晰度（针对 ToDesk 切换时卡几秒）

- 码率每帧连续调整，不分“档位”，不重建编码器。
- 降级顺序：先降画质（码率）→ 再降帧率（只在采集端少采几帧，不改编码器参数，因为改帧率可能触发关键帧）→ 分辨率最后才动，并加滞回，避免来回切换。
- 必须换分辨率时“先接后断”：
  - 新分辨率用第二个编码会话先编好，发一个限制大小的关键帧。
  - 接收端用第二个解码器，新画面能显示了才切换。切换前一直显示旧画面。
- H.264 和 HEVC 换分辨率必须发关键帧；AV1 在标准上支持换分辨率时不发关键帧（参考帧缩放），这是优先用 AV1 的理由之一。

## 4. AI 网络预估（分阶段，v1 就铺好数据管道）

### 4.1 调研结论（报告 C）

- 已在生产环境落地的 AI 带宽估计，都是离线训练加经典算法兜底。
  - 微软 Teams（2025）：用约 100 万通真实通话离线训练，A/B 测试中用户评“差”的通话少了 11.4%。
  - 阿里 OnRL：151 个用户的试验中卡顿减少 14%。
- 纯在线强化学习的拥塞控制，网络条件一变就不稳定。
- 微软 2024 年带宽估计竞赛的冠军用的是 GRU（小型循环网络），也只做到和生产算法持平。

### 4.2 模型设想：交叉注意力 Transformer（与产品负责人讨论后）

- **两路输入**：本机序列（往返时间、在途字节、确认间隔、丢包、帧大小）和对方报告序列（单向延迟变化、接收速率、抖动、Wi-Fi 信号、解码耗时）。
  - 对方报告到达较晚、频率不同，用交叉注意力融合，配真实时间编码。
- **场景信息**：网络类型、直连还是中继、用户是否正在操作、预测的下一帧大小。
- **输出概率分布**，不只输出一个值：未来 50、200、1000 ms 的可用带宽和排队延迟分布，以及未来 500 ms 内骤降的概率。
  - 控制器按风险取值：平时取中位数，用户正在操作时取保守的低分位。
- **规模**：2–4 层，宽度 64–128，上下文约 2.5 秒，参数少于 100 万，int8 量化。单次推理目标 0.1–0.5 ms，待实测。
- **对照**：经典算法、GRU、Transformer 三者在同一套端到端测试里比较。Transformer 要在卡顿、延迟、画质上明显胜出才采用。

### 4.3 训练数据

- 仿真数据有真实数据没有的东西：标准答案（真实瓶颈带宽、排队长度、骤降时刻），可以直接做监督学习。
- **决定：不收集用户数据**。训练数据只来自两处：
  - 我们自己的仿真。
  - 我们自己的实测：CI 和自有机器在各种真实网络上跑。
- **基础模型的目标**：效果追平经典算法即可。之后再做后训练、强化学习，逐步超过经典算法。
- **仿真到真实的落差**这样处理：
  - 仿真器用公开的真实网络轨迹驱动（微软竞赛数据、Lumos5G 等，用前核实许可证）。
  - 仿真参数大范围随机化。
  - 用我们自己实测的数据校准仿真器，并做验证集。
- **骤降的局限**：很多骤降（Wi-Fi 漫游、干扰、家里有人开始下载）无法从网络指标提前预测，要靠信号强度、漫游事件这类系统信号。所以要尽早采集。

### 4.4 安全边界（经典层必须守住）

- AI 只能在一定范围内修正经典估计值（先取 0.7–1.3 倍，有数据支持再放宽）。
- 排队延迟或丢包上升时，经典层立即接管，降码率永远优先于模型。
- 码率有硬上限；模型异常时自动回退；能远程关闭。
- 不从用户那里收集任何网络或屏幕数据。

### 4.5 v1 就要做的

- 码率控制器做成可替换的接口。
- 统一的特征记录格式：每 20 ms 一行，本机和对方的全部特征。只在仿真和我们自己的测试里写出，产品里默认不记录、不上传。
- 仿真器同步记录标准答案。
- 真实网络轨迹回放，批量生成数据集。

## 5. 端到端仿真与实测（从第一天开始）

### 5.1 三层测试

| 层 | 内容 | 频率 |
| --- | --- | --- |
| L1 | 进程内确定性仿真，用真实编码器，按网络轨迹回放 | 每次提交 |
| L2 | 一台 CI 机器上跑真实二进制：Xvfb 虚拟桌面，网络命名空间（netns）加 tbf/htb 做瓶颈、netem 加延迟和丢包（不用本机回环，netem 单独限速时不模拟真实排队） | 每次提交 |
| L3 | 跨机器真实运行 | 每晚 |

### 5.2 指标

- 画质：PSNR、SSIM；关键区域文字 OCR 的错字率。VMAF 对屏幕文字不准，只作参考。
- 变化后多久变清晰（time-to-sharp）。
- 卡顿：两帧之间的最大间隔、超过 100/200 ms 的冻结次数和时长、帧间隔 p99。
- 延迟：被控端画面里叠加帧号条码，控制端识别后算端到端延迟；自动模拟键鼠，测输入到显示的延迟。
- 流量：每种操作的字节数。

### 5.3 必测场景

- 打字、滚动网页、拖窗口、播放视频、切换窗口。
- 带宽 20 → 3 → 20 Mbps 阶梯；瞬间掉 90% 持续 2 秒；往返时间突增叠加丢包。
- **硬门槛**：任何场景不得出现超过 1 秒的冻结。更细的阈值先测基线，再定。

### 5.4 产出

- 每次 CI 生成源画面和接收画面的并排截图、差异热图、短视频，作为构建产物保存。
- 性能数字按提交记录（github-action-benchmark 或 Bencher），能看出哪次提交让效果变差。

## 6. 4K / 8K

- **1.0 目标**：4K60（办公和看电影），硬件编码，GPU 内零拷贝（画面不离开显卡），只缩放一次（按控制端窗口的实际显示尺寸要分辨率）。
- **游戏**：4K120、1080p240，靠硬件编码，并按“条带”编码进一步降低延迟。
- **8K**：消费级只有两条路，放在 1.0 之后：
  - NVIDIA 多编码器分块编码。分两块压缩效率损失约 2%，分三块约 4%；消费卡每台机器最多 8 个并发编码会话。
  - AMD RDNA4 宣称支持 8K75。
- **码率参考**：报告 B 给的是工程估算，待实测校准。

## 7. 接入系统自带的远程桌面

推荐分三步：

1. **端口转发**：经 P2P 隧道转发端口，调用系统自带的客户端。约 2–3 人周。
2. **嵌入 IronRDP**：把 IronRDP 嵌进 PeerDesk 自己的窗口。约 8–12 人周。
   - IronRDP 由 Devolutions 维护，许可证 MIT 或 Apache-2.0（已核实）。
   - 它是不做 IO 的设计，可以跑在任意字节流上，适合走我们的隧道。
3. **远期**：在对方局域网放网关，把远程桌面画面转成 PeerDesk 自己的视频流，享受我们的传输优势。
   - 网关要保存登录凭据，安全风险最高，放在最后。

注意事项：

- **许可证**：libvncclient 和 TigerVNC 是 GPL，RustDesk 是 AGPL，都不能链接进 PeerDesk。
- **macOS**：苹果的“高性能屏幕共享”是私有协议，第三方只能接标准 VNC 加苹果的认证方式。
- **Windows**：家庭版没有远程桌面服务。在 Mac 和 Windows 家庭版上，体验最好的仍是 PeerDesk 自己的被控端。
- **NLA 认证**：经隧道可行，但目标地址写 localhost 时 Kerberos 会失败，只能用 NTLM。

## 8. 建议的开发顺序

1. **端到端测试平台 + 真实编码器**：先让每一步改动都能被客观测量（第 5 节、第 2 节）。
2. **传输算法 v1**：第 3 节全部内容，同时铺好 AI 数据管道（第 4.5 节）。
3. **真实屏幕采集和输入注入**：Linux X11 先行（CI 可测），然后 Windows、macOS。另有远程画面窗口。
4. **4K 硬件编码与零拷贝**：Windows 和 macOS 先行。
