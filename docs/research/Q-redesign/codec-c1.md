# C1：编码后端的接口和契约，以及三个平台后端的搬迁清单（2026-11-27）

对应 `design.md` 3.1 节。接口和契约在代码里：`crates/media/src/backend.rs`（契约九条写在模块说明里，类型和方法照着它定）。
这次做了：定接口；把 openh264 搬到接口后面（`crates/media/src/soft.rs`），逐字节不变。没做：三个平台后端的搬迁（下面是清单）。
产品负责人已定不用 FFmpeg，各平台直接调系统接口，接口没有为 FFmpeg 留特别的口子。

## 1. 接口一览

```
trait EncoderBackend {
    info()        -> 名字、软件还是硬件、码流格式、属性（BackendTraits）
    size()        -> 现在按多大编；None 表示没配置或出错后复位了
    reconfigure(size, rates) -> Reconfigured { rebuilt, keyframe_next }   // 只有它会改尺寸，可以重建
    set_rates(rates)                                                     // 不重建、不出关键帧
    accepts(gpu_frame) -> bool                                           // 认不认这一帧显卡画面
    submit(input, FrameAsk { token, budget, qp, keyframe })
                  -> Ready(Frame | Dropped { why }) | Pending
    poll()        -> Option<Frame | Dropped>                             // 取之前 Pending 的
    flush()                                                              // 让攒着的帧都有下落
}
```

属性（`BackendTraits`）：每帧大小怎么控制（按 QP / 后端自己的码控窗口）、收哪些形式的画面、最多攒几帧、要了关键帧几帧之内给、
新开后第一帧的 QP 限制、整屏突变时会不会自己出关键帧。C2 的体检核对这些属性，并往里加各家的毛病。

## 2. openh264：逐字节不变的证据

- 测试 `software_encoding_is_byte_identical_to_before_the_backend_interface`（`crates/media/src/lib.rs`）：一段固定的操作共 63 帧，
  覆盖软件路径的每个分支（新开按默认 QP、窄带上先初始化再按粗 QP、在变的帧、静止后补清晰、丢帧后要关键帧、整屏变化超限重编、
  换尺寸、奇数宽高、码率估计过期、显卡画面读回）。
- 基准是在搬迁**之前**的提交（dev 2513645）上，另开一个检出、放进同一段脚本录的；搬迁之后 63 帧的“是否出帧、是否关键帧、字节数、码流哈希”全部相同。
- 只在 Linux x86_64 上比哈希（openh264 在别的系统和指令集上不保证每个字节相同），别处只检查跑得通。
- 一处理论上的差别，写明：搬迁前“整屏变化重编”那一次无条件设一遍 QP，现在是“和编码器当前的 QP 不同才设”。只有在之前某次设 QP 失败过、
  而且重编的 QP 恰好等于那次没设上的值时才不一样；设 QP 失败在测试和日志里都没出现过。
- 计时有一点变化（不影响码流）：没有初始化那一次时，编码耗时还是从配置后端之前量到编完；有初始化时改用后端报的计算时间之和。

搬迁中发现的一条：openh264 的屏幕内容模式在整屏突变时会**自己出关键帧**，没要求也出。契约原来写“没要求不许出关键帧”，现在改成
“事先声明了 `scene_keyframes` 的后端可以”，调用方按“可能是关键帧”算预算（现有的重编逻辑已经是这么处理的）。

## 3. 三个平台后端怎么接（交给 Sonnet，带平台标记在 CI 上验证）

做法分三步，前两步不改行为：

1. 每个平台的编码器结构体在保留现有 `HardwareEncoder` 实现的同时，再实现一份 `EncoderBackend`（下面的对照表）。
   平台测试里加一条：同一段输入，两个接口出的码流相同。Windows、macOS 各自带标记跑 CI；VA-API 在有显卡的机器上用 `peerdesk hw-check`。
2. `H264Encoder` 的硬件那条路从 `HardwareEncoder` 换成 `EncoderBackend`（这一步在 Linux 上用假后端就能测，由 Fable 做）：
   `hw_sent` 的“按顺序对号”换成按 token 对号；空帧表示丢帧换成 `Dropped`；`last_rejected` 换成 `Dropped { NotAccepting }`。
3. 删掉 `HardwareEncoder`。

| 契约 | VideoToolbox（`vt.rs`） | Media Foundation（`mf.rs`） | VA-API（`vaapi.rs`，cros-codecs） |
| --- | --- | --- | --- |
| token 带回 | 每帧的 `sourceFrameRefCon` 原样回到输出回调，直接放 token | 输入样本的时间戳设成 token，输出样本读回来（现在设的是帧序号 × 时长，改成 token 即可） | 输入帧的元数据带时间戳，输出里读回；编码线程和通道里一起传 |
| 丢帧要明说 | 输出回调的 `infoFlags` 有“帧被丢了”的标志，转成 `Dropped { Budget }`（现在是交一个空帧） | **冲突，见下面第 1 条** | 待核对 cros-codecs 有没有丢帧的回报；没有的话同 Media Foundation 的办法 |
| 这会儿不收 | 没有这种情况 | `MF_E_NOTACCEPTING` → `Dropped { NotAccepting }` | 通道满 → `Dropped { NotAccepting }` |
| 还没好有上限 | 属性里 `max_held` 按 `MaxFrameDelayCount` 设的值声明；Intel Mac 攒 1 帧 | 异步：声明 `max_held`（先按 2），超过的按下面第 1 条处理 | 同左 |
| 要关键帧 | 强制关键帧的选项；苹果文档说“不保证都能满足”，**见第 2 条** | `CODECAPI_AVEncVideoForceKeyFrame`；个别厂商的编码器不支持按需关键帧，**见第 3 条** | 提交关键帧类型 |
| 改码率不重建 | 改会话属性（平均码率和数据率上限），已经是这样 | 改 `CODECAPI_AVEncCommonMeanBitRate`；有的编码器运行中不接受，**见第 4 条** | 已有 |
| 改帧率不重建 | **见第 5 条** | **见第 5 条** | **见第 5 条** |
| 改尺寸 | 新建会话：`rebuilt`、`keyframe_next` 都为真 | 重建 | 重建 |
| 停多久都行 | 没有内部超时 | fpsfix 第 1 步已修（计时从交帧算起） | 待核对通道超时 |
| 时间分开报 | 计算 = 交帧到出帧；等待 = 0（显卡画面不读回） | 计算 = 交帧到出帧；等待 = 读回显卡画面和等“要输入”事件 | 计算 = 交帧到出帧；等待 = 通道里排队 |
| 画面形式 | NV12 内存、显卡画面（CVPixelBuffer，`accepts` 已有） | NV12 内存（显卡纹理等零拷贝那一步） | NV12 内存 |
| 码控 | 后端自己的窗口（`Window`） | 同左 | 同左 |

### 和契约冲突的地方

1. **Media Foundation 被码控丢掉的帧没有任何通知**（契约第 1 条：每帧都有下落）。交进去的帧只是不出来，分不清“丢了”和“还没好”。
   办法（闭环，不靠超时）：这些编码器不重排帧（没有 B 帧），输出一定按输入的顺序。所以**后面的 token 出来了，前面还没出来的就是丢了**，
   在出帧的那一刻把它们报成 `Dropped { Budget }`；`flush` 结束时还没出来的也一样。属性里声明“按顺序出帧”。
   要先确认的一点：各家的编码器是否都把输入样本的时间戳原样带到输出（Intel 的现在是按序号设的，没验证过读回）。带不回来的厂商只能按顺序对号，
   属性里标出来，体检负责发现。
2. **VideoToolbox 不保证满足关键帧要求**（契约第 3 条）。码率窗口放不下时它把要求的关键帧丢掉。按契约这要回 `Dropped { Budget }`，
   调用方接着要，并且把预算抬到放得下为止（fpsfix 第 1 步的“丢一次、下限翻倍”，C3 里并进预算核对）。`keyframe_within` 对它的含义是
   “预算够的前提下几帧之内给”，属性说明里写清。
3. **个别厂商的 Media Foundation 编码器不支持按需关键帧**（调研里 Sunshine 把它标成固定 GOP；我们在 Intel 上用着是好的）。
   这种后端不满足契约、不能用：体检查出来就不选它，退到软件编码，并告诉用户原因。不为它在上层绕。
4. **有的 Media Foundation 编码器运行中改不了码率**（契约第 5 条）。`set_rates` 必须如实返回失败；调用方改用 `reconfigure`
   （重建，代价是一个关键帧），并且对这个后端把“改码率”的频率压下来（变化不到三分之一不下发，Chromium 远程桌面的做法）。属性里标出来。
5. **改帧率**（契约第 5 条）：Media Foundation 的帧率在媒体类型里，改它等于重建；VideoToolbox 的期望帧率只是提示。
   办法：后端的帧率在配置时定死（按最高帧率），之后不改；`set_rates` 里的帧率只用来把每帧预算换算成码率
   （码率 = 预算 × 8 × 后端配置的帧率）。这样“改帧率”对后端来说只是改码率，三个后端都不用动编码器。

以上五条里，1 和 5 是搬迁时就要按这里写的做的；2、3、4 是把现有的处理方式换成契约里的说法，行为不变。

## 4. 拿不准的地方

- Media Foundation 各家编码器是否原样带回时间戳（上面第 1 条的前提），没有验证过。
- 把“计算时间”对硬件定义成“交帧到出帧”是否合适：它包含编码器内部的排队。C3 做预算核对时再看要不要拆。
- 接口里没有参考帧失效、帧内刷新、长期参考帧：现在没有后端用。等接 NVENC 原生接口时加可选方法；到时如果发现要改 `FrameAsk`，现有后端要跟着改一处。
- 每帧 QP 对硬件后端（Media Foundation 的逐帧 QP、NVENC 的固定 QP 模式）能不能做到和 openh264 一样准，没有数据；所以属性里分了“按 QP”和“码控窗口”两种，
  不假设硬件能按 QP。
- 新代码里有几行测试走不到：openh264 打开失败、编码失败这两个出错分支（造不出这种失败），覆盖率可能掉一点。
- AV1 只在 `Format` 里占了一个名字，接口没有按 AV1 的特点（屏幕内容工具开关、tile）验证过，C6 时再对。

## 5. 审查意见（主会话，2026-11-27）

接口和契约通过。逐字节不变的测试是好证据。五条冲突的处理都讲得通，没有绕过问题。搬迁时按下面三点改：

1. **送进编码器的时间戳，不能直接用 token。**
   - 原因：Media Foundation、VideoToolbox 的码控都会看输入时间戳，按“码率 × 两帧间隔”给每帧分配大小。
     token 是调用方起的编号，可能跳号（例如没交给后端的帧也占了编号）。直接拿 token 当时间戳，码控看到的帧间隔就乱了。
     这样“改帧率只换算成码率”（第 5 条）的前提也被破坏了。
   - 做法：后端内部按交帧的顺序编号，时间戳 = 顺序号 × 配置帧率下的帧间隔（就是现在的做法）。另外留一张“顺序号 → token”的表。
     出帧时用顺序号查回 token，按顺序判丢帧（第 1 条）也用顺序号。
   - VideoToolbox 的 `sourceFrameRefCon` 和时间戳是两回事，可以直接放 token，但时间戳同样按顺序号给。
2. **硬件的“计算时间”不能直接当帧率上限的依据。**
   - 原因：异步编码器攒着帧时，“交帧到出帧”里包含排队，会被误判成“编码跟不上”。
   - 做法：契约第 8 条对硬件后端补一句，计算时间是延迟，不是吞吐。
     帧率上限估计器（B2）对硬件看吞吐：连续交帧时每秒实际出几帧。对软件看计算时间。
   - C3 的预算核对和 B2 都按这个来。
3. **能力协商要用的字段，C4 时补进 `BackendInfo`**：
   - 档次和级别（4K60 要 5.2 级）；
   - 色度（4:2:0 / 4:4:4）；
   - 位深；
   - 最大尺寸和帧率（实测值）。

   现在不加，免得没有数据时先写死。
