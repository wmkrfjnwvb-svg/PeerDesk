# 整体重新设计的要求（产品负责人，2026-11-27）

不要修修补补。给一个通用框架，以后遇到新场景不用逐个微调。

**核心是两件事：适合我们的框架，和适合我们的仿真。**
- 其余各项都挂在这两件事上：编解码层、能力协商、界面切换、对手对比。
- 设计文档先把这两件做透，其余部分写清接口和顺序即可。
- “适合我们”指的是远程桌面的特点：
  - 大部分时间静止、突然爆发；
  - 看文字，清晰度最后让步；
  - 硬件差异大；
  - 弱网、跨网、局域网都要好。
- 不照搬为视频通话设计的 WebRTC。

## 核心目标（产品负责人原话，编号照原样）

1. 清晰度优先：帧率和码率不够时再调分辨率，先保持清晰度。
2. 帧率保持住，并且是最优。
3. 码率保持住，并且是最优。
4. 能仿真各种网络。
5. 覆盖弱网、跨网、局域网。
6. 网络切换要丝滑：切换时可以中断，但连上以后必须完美。用户能接受切网络时的中断。
7. 自适应。
9. 硬编解码优先：只要硬件能用就不用软件。用户可以自己选硬件或软件。
10. 软件和硬件效果一样。产品负责人的看法是两者只差延迟，别的不该有差别。

11. 支持 720p、1080p、2K、4K。用户可以自己选，选了以后帧率、码率要保持住。
12. 支持电影、游戏、设计等高清画质。
    - 产品负责人说：这块很难，但这才是核心竞争力，其他都是锦上添花。要深入调查。

13. 能力协商，像 WebRTC 交换 SDP 一样：
    - 两端交换各自的能力，选出双方都支持的最优组合。
    - 能力可以提前探测：我们有服务端，连接之前就能知道。
    - 目标电脑不支持某项时，靠协商找最优，不是直接失败。

14. 框架要能支持 4K、8K，但能不能用要看两端支不支持，不支持就用不了。
    - 软件编解码到 2K 就有点吃力。
    - 以 H.264 为主；高分辨率要上 AV1；HEVC 情况不清楚，要查。

15. 能力用在界面上：
    - 两端都支持更好的画质时，在远程设备那里提示用户可以用更好的画质（例如“这台支持 4K60”）。
    - 用户点进去，觉得好就继续用。
    - 觉得不行，在会话助手（工具条）里切换帧率、码率、分辨率等。

16. （我加的，产品负责人说“要做透，把对手打穿”）和对手用同一把尺子比：
    - 网络条件相同：同一条轨迹，用 Linux 路由器的 tc，或系统自带的限速工具，回放到真实网络上。
    - 同时跑 PeerDesk、Parsec、ToDesk，量同一组指标：画面延迟（手机高速摄像拍两块屏）、冻结、字的清晰度、流量。
    - 差距写进文档。我们的门槛按“不比对手差”定，只升不降。
    - 设计里要给出这套对比测量怎么做。
    - **必须全自动，不能靠产品负责人手动**，否则仿真和对比没法持续。
      - 产品负责人会把自己的 Windows 和 Mac 接进 GitHub Actions，作为自托管运行器。
      - 开源对手（RustDesk、Sunshine/Moonlight）可以下载下来，用命令行驱动。
      - 闭源对手（Parsec、ToDesk）用脚本驱动界面：Windows 用 UI Automation，macOS 用辅助功能接口。
      - 限速用脚本回放轨迹：macOS 用 dnctl/pf，Windows 用基于 WinDivert 的工具，Linux 用 tc。
      - 延迟不靠摄像头：被控端屏幕上画时间码，控制端截图读出时间码，再扣掉两台机器的时钟差。
    - 仓库是公开的，自托管运行器有安全风险：
      - 只用推送触发，不用 PR 触发；
      - 仓库设置里，外部人员的 PR 一律要人工批准才能跑；
      - 运行器用单独的系统账户。
    - 测试会占用屏幕和键鼠，不能在产品负责人正在用电脑时跑。放在空闲时段，或用不常用的机器。

### 设计时要讲清楚的几点（我的理解，产品负责人可以改）

- **15 会话中切换**：
  - 切换不断开、不卡：分辨率先接后断，码率和帧率连续调整，和现有规矩一致。
  - 工具条同时显示两组值：用户设的目标，和实际做到的（帧率、码率、分辨率、编码器是硬件还是软件）。做不到时写明原因，例如“对方解码只到 4K30”或“网络只够 8 Mbps”。
  - 码率给用户的形式：可以是画质档位，或者码率上限（例如手机流量时省流）。设计里定。
  - 用户的选择按设备记住，下次连接沿用。

- **14 编码格式分层**：
  - 框架本身不写死分辨率和编码格式的上限，上限来自能力协商（第 13 条）。
  - H.264 标准本身支持 4K（级别 5.1 约 4K30，5.2 约 4K60，6.x 可到 8K）。实际卡在两处：
    - 硬件对 H.264 的支持（编码宽度、解码级别）；
    - 同样画质下码率比 HEVC/AV1 高，分辨率越高越吃亏。
  - 所以 H.264 为主；高分辨率在两端都支持时协商用 HEVC 或 AV1，不支持就如实告诉用户。
  - HEVC 有专利费问题，AV1 硬件支持较新，两个都要查清楚再定。

- **13 能力协商**：
  - 现状：握手里只有一个能力位图（例如 PROBE_ID 在第 31 位），不够用。
  - 要交换的能力：编码器和解码器（硬件或软件、H.264/HEVC/AV1、最高分辨率和帧率、是否支持 4:4:4 和 10 位）、屏幕（分辨率、缩放、刷新率）。
  - 声明的能力不等于实际能做到。驱动有毛病、硬件编码会中途失败。所以分三层：
    1. 先声明；
    2. 本机实测一次（启动时或第一次会话时短测），结果缓存；
    3. 会话中做不到时重新协商，并告诉用户原因。
  - 被控端上线时把能力报给服务端：
    - 好处：控制端连之前就知道能做到什么，设备列表里能直接显示“支持 4K60”，和设备管理接上。
    - 隐私：只报能力，不报序列号这类能认出具体机器的信息。
  - 业内参照：WebRTC 的 SDP offer/answer、编码参数协商。

- **11、12 是“能力上限”问题**：每一环都要算清 4K60 够不够，最慢的一环决定上限。
  - 各环：采集、颜色转换、编码、网络、对方解码、显示。
  - 4K 每帧约 830 万像素，是 1080p 的 4 倍。软件编码大概率撑不住，H.264 的级别上限、硬件解码的支持也要查。
  - 做不到时要如实告诉用户：卡在哪一环、建议怎么办。不能静默降级。
  - 设计模式要考虑 4:4:4 色度（彩色细字、设计稿）。
  - 电影模式要考虑帧节奏，例如 24 帧片源按 24 帧送。
  - 游戏模式要考虑最低延迟。
  - 资料：`industry-hires-quality.md`（在查），已有的 `docs/research/O-modes-industry.md`。

- **1、2、3 之间的取舍**：带宽不够时只有三条路：每帧变糊、帧率降低、分辨率降低。
  - 理解的顺序是：“字看得清”是底线，要定义成可测的量（例如 QP 上限，或文字区域的清晰度指标），不能破。
  - 在底线以内，画质可以先让一点。
  - 然后降帧率。静止和打字时降帧率几乎看不出来。
  - 分辨率最后才降，并且先接后断，不卡。
  - 这和 WebRTC 共享屏幕默认的“保分辨率、降帧率”一致。
- **“最优”要有定义**：在当前网络和设备上，满足清晰度底线的前提下，帧率和码率最高，且不来回跳。设计里要写成可测的指标，进门槛。
- **10 要拆成能做到和要量的两部分**：
  - 能做到的：码率、帧率、分辨率的决定全部由我们的控制层做，编码器只执行，不信任硬件自带的码率控制（WebRTC 也是这样）。这样软件和硬件的行为一样，差别只在速度。
  - 要量的：同样码率下，不同编码器的画质本身有差别。要在屏幕内容上实测（每家硬件、openh264），写进门槛，不能假设没有差别。
  - 软件编码也要达标：1080p 软件编码至少稳定 20–30 帧。现在 Windows 上软件编码“很废”，要查清根因。

## 码率、帧率的通用框架

1. 会话开头有 2–5 秒的前置探测期，自动测出：
   - 带宽（这条网络能稳定承载的码率）；
   - 网络类型（有线局域网、Wi-Fi、蜂窝、跨洋高延迟等，按实测特征判断，不按地址猜）；
   - 能维持的帧率上限（采集、编码、网络、对方解码里最慢的那一环）；
   - 由此得出的最优策略（码率、帧率、分辨率的组合）。
2. 探测完毕必须稳定、丝滑：码率和帧率不来回跳。
3. 通话过程中保持稳定；网络抖动时完美自适应（小抖动吸收，真变差才降，恢复后平稳回升）。
4. 用户切换网络或断网重连时，从第 1 步重新开始。
5. 用户可以自己设置帧率、分辨率：
   - 设定值是目标或上限；
   - 维持不了就自动降低，并告诉用户原因；
   - 默认不设，走自动探测出的最优策略。

## 量尺（核心）

- **仿真是核心**：产品负责人不可能在真机上找到各种场景。量尺要能自己生成和覆盖各种网络，新框架靠它验证“能自适应各种网络”。
- 现在的仿真太简单（“太傻”），靠我们预设的几个场景。
- 研究业内网络仿真怎么做（Mahimahi、ns-3、Pantheon、WebRTC 的网络仿真、OpenNetLab/AlphaRTC 等），整体设计我们的仿真。
- 要用微软 MMSys 2024 数据集里全部的仿真数据和真实网络数据，构建完善的网络类型和流量类型（操作类型：静止、打字、滚动、切窗口、看视频等）。
- 加上我们自己的用户日志（docs/research/data/user-logs/）。

## 编解码

- 现在的编解码让我们很被动（各厂商编码器行为不一、关键帧被丢、读回显卡画面慢）。
- 深入研究业内开源怎么做，设计一个通用的编解码层。

## 方法

- 深入研究业内开源，根据我们的目标整体设计：哪些参考、哪些不参考，写明理由。
- 结合远程桌面的特点：大部分时间静止、突然爆发、看文字（清晰度最后让步）。
- 先出设计，产品负责人看过再动手实现。
- 现在的修复（fpsfix 第 2、3 步）先暂存，从仿真、算法框架架构整体重新研究和设计。
