# A1：全模型仿真（L0）的实现方案（2026-11-27）

对应 `design.md` 1.2 节的 L0 和第 6 节的 A1。目标：控制逻辑全部用产品的真实代码，只把“像素、真编码、真解码”换掉，快到能跑上万次会话。

## 1. 现状：能直接用的和绑死的

`crates/e2e/src/lib.rs` 的 `run()` 已经是我们要的骨架：虚拟时间、单线程、事件推进，`MediaSender`、`MediaReceiver`、节奏器、反馈、重传、纠错、
探测都是产品代码，网络是 `core::sim::Net`。所以 L0 **不另起一套仿真**，是同一个 `run()` 换三个零件。
（`core/src/desktop_sim.rs` 是更早的一版，用老的 `RateController` 和块编码，不走 `MediaSender`；A1 不动它，A5 时删或标成过时。）

和像素、真编码器绑死的地方（都要先拆）：

| 在哪 | 绑在什么上 | 怎么拆 |
| --- | --- | --- |
| `e2e::run()` 开头 `RealisticDesktop::new`、循环里 `desk.step()`、`desk.screen()` | 画面来源只能是合成像素 | 抽一个“画面来源”接口：`step(操作) -> 变没变`、`frame() -> 交给发送端的一帧`、`version() -> 内容版本号` |
| `tx.on_frame(now, &Screen, ..)`（`core/src/media.rs`） | 入口只收像素 | 加一个收“帧的引用”的入口（像素 / 显卡画面 / 内容描述），`on_frame` 改成调它；产品已经走 `start_frame` + `encode_job(&Frame)` 这条路，不受影响 |
| `H264Encoder::encode_input`（`media/src/lib.rs`）的 `Input::{Rgb, Gpu}` | 先转颜色、从像素抽样算变化面积，再交后端 | 加第三种输入“内容描述”：跳过转换，面积和细节直接取描述里的；QP 控制、大帧规则、补清晰、超限重编这些**真逻辑一行不跳** |
| `H264Encoder` 的软件后端写死是 `OpenH264Backend::new()` | 换不了后端 | 加 `with_soft_backend(Box<dyn EncoderBackend>)` |
| `FrameInput`（`media/src/backend.rs`）只有 I420、NV12、显卡画面 | 假后端只能从像素平面算面积和细节 | 加 `FrameInput::Described(&ContentDesc)`，`Inputs` 加一位；只有假后端声明收它 |
| `e2e::run()` 里 `rx.on_datagram()` 当场解码、`luma_psnr(显示的, 源)` 判清晰、算等待 | 显示端的指标全靠像素比较 | 抽一个“显示端量尺”接口：`on_shown(画面, 时刻)`、`sharp() -> 是否清晰`、`caught_up() -> 是否已经是最新内容`；像素版就是现在的代码，L0 版按内容版本号和 QP 判 |
| `CodecKind::make()` 只会造真编码器、真解码器 | – | 加两种：假后端吃真像素（下面叫 L0.5）、假后端吃内容描述（L0） |

要新加的类型（放 `core`，纯数据）：

```
ContentDesc { version: u64,            // 源画面第几版（每变一次加一）
              size: (u16, u16),
              class: 操作类别,          // 和 M2 的类别一一对应
              changed_permille: u32,   // 和上一版比变了多少（产品里同一个抽样算法的结果）
              detail_permille: u32 }   // 细节
Shown       { version: u64, qp: u8, key: bool }   // 解码端“显示出来的是什么”
```

假码流要能被假解码器读：帧头后面带 `Shown`，其余是填充字节（长度由字节模型定）。假解码器检查参考链（上一帧没解就报错，和真解码器一样会触发“等关键帧”），
交出 `Picture::Described(Shown)`。接收端走产品控制端用的延后解码那条路（`on_datagram_deferred` + `ReceiverDecoder`），不走仿真专用的当场解码。

**同一次会话在 L1 和 L0 里必须是同一份内容**，否则没法对账。做法：先让像素版的合成桌面跑一遍，用产品里的算法（M2 方案第 0 节要提出来的那两个函数）
算出每一拍的 `ContentDesc`，存成“操作时间线”；L0 重放这条时间线，不生成像素。以后会话记录回放、操作模型生成的也是这种时间线，L0 只认它。

L0 里的清晰度代理：显示的版本等于源的版本、而且 QP ≤ `QP_sharp` 算“清晰”；QP > `QP_text` 的时间算“破底线”（两个值在 M3 出数之前用占位，结果只报告）。
“等待”的定义和 L1 相同：源变了一版，到显示端出现不低于这一版的画面为止。

## 2. 虚拟时间、随机数、世界文件

- **虚拟时间、单线程**：已经是。假后端的时钟（C2 的 `Clock`）接到 `run()` 的 `now`。A1 里编码、解码耗时都按 0 算（和 L1 现在一样，才能对账）；
  设备耗时模型是后面的事，接口已经在假后端里。
- **随机数**：`core::sim::Net::new(seed)` 现在所有网络毛病共用一条随机数流，合成桌面另有一条。拆成“每层一条、由（世界种子，层的名字）导出”会改变每一个现有场景的结果，
  144 次基线和回归门槛都要重录。所以 **A1 不拆**：现有场景保持老的取数顺序（标成“随机数布局 1”）；A2 加新的网络层时引入“布局 2”（每层独立），
  新的世界文件用布局 2，老场景继续用布局 1 直到基线迁移。A1 只保证新加的东西（字节模型的残差扰动）用自己独立的一条流，不动老的。
- **世界文件**：一次会话的全部输入，文本，一行一个键值，`#` 开头是注释；按内容哈希命名。A1 的内容：画面尺寸和帧率、网络（现有 `Scenario::network` 的那些字段，
  带生效时刻）、操作（阶段列表，或指向一条操作时间线文件）、编解码种类和模型文件、估计器和策略、种子、随机数布局号。`Scenario` 和它互相转换，
  “读进来再写出去”逐字节相同。工作区没有通用的序列化库，自己写（和服务端的 `json.rs`、设备表日志同一个路数）。

## 3. 速度

**先量，再承诺。** 第一步重构时就在 `run()` 的各段加计时（环境变量打开，不影响结果）：画面生成、转颜色加编码、分片纠错和发送、网络推进、收包重组、解码、
比较画面、其余。手头唯一的实测是：`real_log_rhythm`（720p、60 帧每秒、约 27 秒会话）release 下跑 46 秒，约 0.6 倍实时。

估计（没量过，第一步的计时表会证实或推翻）：这 46 秒里绝大部分是每帧的像素活——画合成桌面、RGB 转 I420、openh264 编码、解码、两幅 92 万像素的画面算信噪比，
合计每帧二十几毫秒。L0 把这些全去掉，剩下的开销和包数成正比：办公内容平均每秒几十到一百个包、50 份反馈、60 拍，每样几微秒，估计每仿真一秒花 1–5 毫秒，
也就是 200–1000 倍。看视频、滚动这类每秒上千个包的时段会低到几十倍（纠错是对真实字节算的）。所以“500 倍”对以静止为主的办公会话有希望，对全程高码率的会话达不到；
如果计时表显示“其余”那一项就已经超过每秒 2 毫秒，要先看是谁（最可能是纠错编码和每包的内存分配），再决定是优化它还是下调目标。

量法（写进 S5 的报告）：一批固定的会话（现有回归场景加 12 条微软轨迹各 3 个种子），单线程 release，`仿真的总秒数 ÷ 墙上秒数`，分“办公”“视频”两组报；
另报多进程并行后的每小时会话数。

## 4. L0 对 L1 的对账

三方一起跑同一批会话，分开两种误差来源：

| 档 | 画面 | 编码 | 用来看什么 |
| --- | --- | --- | --- |
| L1 | 真像素 | 真 openh264、真解码 | 基准 |
| L0.5 | 真像素 | 假后端（面积、细节从像素算）+ 字节模型 | 只差“字节模型准不准” |
| L0 | 操作时间线（内容描述） | 假后端 + 字节模型 | 再加上“内容描述够不够” |

比什么（每个会话一行，三档各一列）：总字节；每两秒窗口的字节（相对误差的中位和 90% 分位）；发出的帧数、关键帧数；冻结次数、最长等待；
码率的中位和 5% 分位；各码率状态的时间占比；降码率次数、帧率换档次数；探测的轮数和结论。

容差：两秒窗口字节的相对误差中位 ≤15%、90% 分位 ≤30%（M2 方案的判据 2）；帧数差 ≤5%；冻结、换档这类计数先只看方向一致。
**M2 没量完之前**假后端用占位的 `DefaultByteModel`，流程照跑，对账的数字只报告、不当门槛；M2 的模型文件到了换上再判。
会话在某个时刻走岔之后单次轨迹没有可比性（一个字节的差别就会岔开），所以对账看的是一批会话上这些量的分布，不是逐帧对齐。

## 5. 分步

| 步 | 内容 | 谁 | 验收 |
| --- | --- | --- | --- |
| S1 | **不改行为的重构**：`e2e::run()` 拆出“画面来源”“显示端量尺”两个接口，像素版实现就是现在的代码；`MediaSender` 加收帧引用的入口，`on_frame` 改成调它；各段计时 | Fable | 重构前先录基准：全部端到端仿真场景和 12 条微软轨迹各 1 个种子的 `Outcome`（每份反馈的特征行、各项计数、每阶段结果）的哈希；重构后逐字节相同。产出计时表，第 3 节的估计据此修正 |
| S2 | 提出“变化面积”“细节”两个函数（M2 也要）；`H264Encoder::with_soft_backend`；假解码器和 `Picture::Described`；`CodecKind` 加 L0.5（假后端吃真像素）；接收端改走延后解码那条路 | Sonnet（接口由 Fable 在 S1 里定好） | C1 的 63 帧逐字节测试仍过；S1 的基准仍逐字节相同（L1 没动）；L0.5 能跑完全部场景，没有花屏计数；假解码器对“缺参考帧”的反应和真解码器一致（单元测试） |
| S3 | `ContentDesc`、`FrameInput::Described`、`H264Encoder` 的第三种输入；从像素桌面导出操作时间线；`CodecKind` 加 L0；L0 的显示端量尺（版本号、QP） | Fable | 同一会话 L0.5 和 L0 交给假后端的（面积, 细节, QP）序列逐帧相同（这证明内容描述没有丢信息）；L0 全部场景跑通；S1 基准不变 |
| S4 | 世界文件的读写和内容哈希；批量运行器（一批世界文件、多进程、每会话一行 CSV） | Sonnet | `Scenario` 往返逐字节相同；同一个世界文件跑两遍结果相同；批量结果和单个跑的一致 |
| S5 | 对账报告（L1、L0.5、L0 三档，第 4 节的量）和速度报告（第 3 节的量法）；结果写回本文档 | Fable | 两份报告有数；达没达到 500 倍、对账差多少都如实写；没达到的给出原因和下一步（优化哪一段，或者下调目标） |

S1 做完如果计时表显示去掉像素之后仍然到不了 100 倍，先停下来汇报，不接着做 S2。
S2、S4 可以和 S3 并行（S2 的接口定了以后）。每步单独提交；S1、S3、S5 要整跑端到端仿真，等磁盘空出来排队。

## 6. 不在 A1 里的

设备耗时模型（编码、解码要时间）、新的网络层和每层独立的随机数（A2）、类型抽样和数据导入（A3）、会话记录回放（A4）、统计和门槛（A5）、自动搜索（A6）。
A1 只回答两个问题：L0 能多快；它和 L1 差多少。

## 7. 拿不准的

- 速度是估的，S1 的计时表之前没有数。
- 假后端按内容描述出字节，补清晰那几帧（内容不变、QP 一步步降）和“超限重编成关键帧”的字节数靠字节模型，M2 里这两种最可能不准；对账时单独列出来。
- 走延后解码那条路之后，L1 的时序会不会和现在差一点（当场解码变成隔一步解码）：如果会，S2 的“基准逐字节相同”就做不到，那一项改成只在 L0、L0.5 里走新路，L1 保持原样。

## 8. S1 的结果（2026-11-27）

**逐字节不变。** 重构之前先加了结果指纹（`crates/e2e/src/lib.rs` 的 `fingerprint`：除调试记录以外的每个数、每个阶段结束时两端的画面像素），
用 release 跑全量端到端仿真录了基准（104 次运行：全部回归场景、记录仪的对照测试、12 条微软轨迹各 3 个种子）；重构之后 104 行全部相同。
基准在 `crates/e2e/golden/fingerprints.txt`，比对脚本是 `scripts/e2e-fingerprints.sh`（以后每次“不改行为”的重构都用它；算法本来要变的改动用 `--update` 重录）。
基准里另有 2 行是这次新加的单元测试自己跑的会话。

**分段计时**（`PEERDESK_E2E_PROFILE=1`，release，单线程，45 次会话共仿真 1278 秒，墙上 467 秒，现在是 2.7 倍实时）：

| 段 | 墙上时间 | 占比 | 每仿真一秒 |
| --- | --- | --- | --- |
| 编码和切片（转颜色、openh264、切片、纠错） | 192.8 秒 | 41.3% | 150.9 ms |
| 生成画面（合成桌面） | 105.6 秒 | 22.6% | 82.7 ms |
| 显示端量尺（比两幅画面的亮度信噪比） | 99.0 秒 | 21.2% | 77.5 ms |
| 收齐并解码 | 66.3 秒 | 14.2% | 51.9 ms |
| 其余（建会话、阶段结束时拷贝画面、汇总结果） | 2.1 秒 | 0.5% | 1.66 ms |
| 反馈和控制（码率控制、重传、定时任务、出反馈） | 0.3 秒 | 0.1% | 0.23 ms |
| 出包（节奏器、封数据报） | 0.1 秒 | 0.0% | 0.12 ms |
| 收包重组（没收齐帧的数据报） | 0.1 秒 | 0.0% | 0.10 ms |
| 仿真网络 | 0.1 秒 | 0.0% | 0.07 ms |

和像素有关的四项占 99.4%。传输和控制的全部真实代码（反馈和控制、出包、收包重组、仿真网络）合起来每仿真一秒只要约 0.5 ms。

**L0 能到多少倍**：去掉像素四项后每仿真一秒剩 2.2 ms，约 460 倍；按场景分：办公 240–280 倍，极窄带和窄带视频 110–140 倍，微软轨迹 520 倍。
这是从现有数字推的上限，有两处没算准：
- “编码和切片”里切片、纠错那一部分 L0 还要做，没法从这一项里分出来；按“收包重组”每秒 0.1 ms 的量级看很小。
- “其余”那 1.66 ms 多半是每次会话固定的开销（建合成桌面、每个阶段结束拷贝两幅画面），L0 里大部分也没有了；会话越长它摊得越薄。

所以 L0 的预期是 300–1000 倍（办公内容），高码率内容 100 倍出头；过了“到不了 100 倍就停”的线，500 倍对办公会话有希望，要等 S3 的 L0 跑起来才是实测。
多进程并行另算：本机全量端到端仿真用户态 17 分钟、墙上 5.7 分钟，大约 3 个核在干活。

## 9. S2 的结果（Sonnet，2026-11-27）

- 新增 `crates/media/src/content.rs`：变化面积（`AreaSampler`）和细节（`detail_permille` 等）提成共用的函数，产品、假后端、M2 用同一份。
- `H264Encoder::with_soft_backend`；假解码器（`FakeDecoder`，缺参考帧时报错并拒收，直到关键帧）；`Picture::Described`。
- `CodecKind::H264L05`（L0.5：真像素交给假后端），接收端走控制端同一条延后解码的路；L1 原样没动。
- 指纹 108 行全同（比 S1 多 2 行，是新加的 2 个 L0.5 单元测试会话）。
- L0.5 跑全量：花屏 0；冻结合计 L1 129 次、L0.5 68 次；最长等待的均值 244 ms 对 156 ms。字节模型还是占位的，这些数只报告。
- L0.5 的速度 5.8 倍实时，大头是合成桌面（每仿真一秒 86 ms）和颜色转换、变化面积抽样（75 ms）。
- 第 7 节最后一条（延后解码会不会改变 L1 的时序）没有验证：L1 没改。

## 10. S3 的结果（2026-11-27）

**做了什么**
- `core::frame::ContentDesc`：一幅画面的内容描述，没有像素，只有编码这条路上真正用到的抽样——编码器估计变化面积用的抽样点和细节量（原尺寸上取），
  每种可能的编码尺寸（原尺寸、降分辨率时的半尺寸）各一份亮度抽样和细节。
  带的是**抽样本身**而不是“变了千分之几”：变了多少要和上一次编的那一幅比，而上一次编的是哪一幅取决于发送端当时跳没跳帧，事先算不出来。
- `VideoEncoder::encode_described`、`MediaSender::on_described`；`H264Encoder` 的第三种输入：不转颜色、不走硬件，变化面积走 `AreaSampler::observe_sample`
  （和从像素算是同一段比较代码），QP 控制、大帧规则、补清晰、超限重编一行没跳。
- `FrameInput::Described`、`Inputs::described`；假后端收到它时抽样、细节、版本号直接取，不再从亮度平面算。
- `peerdesk_media::content::describe`：把一幅画面变成内容描述，亮度平面的算法和编码器转换画面时完全一样。
- `crates/e2e/src/timeline.rs`：操作时间线。把像素版合成桌面按场景的阶段跑一遍，每变一版取一份描述；按（尺寸、种子、阶段）缓存最近 3 条。
- `CodecKind::H264L0`、`TimelineStage`（重放时间线，按版本号和 QP 判清晰，和 L0.5 同一个判据）；环境变量 `PEERDESK_E2E_CODEC=h264-l0` 把默认场景都换成 L0。

**验收**
- **L0 和 L0.5 的会话一模一样。** 比的是“行为指纹”（`behaviour_fingerprint`：每份反馈的特征行、各项计数、每阶段的流量和等待，不含编码档的名字和像素）。
  这比“交给假后端的（面积, 细节, QP）逐帧相同”更强：那些数只要有一帧不同，后面的字节、码率、反馈就全不同。
  - 永久测试 `tests/l0.rs`：5 个场景（局域网、600 kbps 窄带、蜂窝、5% 丢包 60 帧、带宽阶跃），七种操作都有，全部相同。
  - 全量：全部端到端场景加 12 条微软轨迹各 3 个种子，分别按 L0.5 和 L0 跑，113 次运行的行为指纹全部相同（`PEERDESK_E2E_BEHAVIOUR` 导出后排序比较）。
- **L0 跑通全部场景**，花屏 0。有 4 个测试在 L0 和 L0.5 下同样不过（三个清晰度、探测的门槛，一个记录仪的对照），原因是占位的字节模型，L1 下都过；M2 的模型换上之后再看。
- **S1 的基准不变**：指纹文件从 108 行变成 118 行，只追加了 `tests/l0.rs` 的 10 次会话，旧行一行没动。

**L0 的实测速度**（release，单线程，77 次会话共仿真 1672 秒；只算会话循环，不算导出时间线）

| 场景类型 | 次数 | 仿真 | 会话循环 | 倍实时 |
| --- | --- | --- | --- | --- |
| 微软轨迹（办公混合，33 秒一次） | 36 | 1188 秒 | 1.9 秒 | 624 |
| 窄带、蜂窝办公 | 10 | 138 秒 | 0.27 秒 | 507 |
| 窄带看视频 | 3 | 18 秒 | 0.04 秒 | 419 |
| 宽带办公、探测、丢包、带宽阶跃 | 27 | 318 秒 | 0.77 秒 | 410 |
| 大屏 2880×1800 | 1 | 10 秒 | 0.025 秒 | 400 |
| **合计** | 77 | 1672 秒 | 3.0 秒 | **554**（中位 550，最慢约 200，最快 3000） |

会话循环里每仿真一秒 1.8 ms：编码和切片 1.28 ms（面积比较、7 万字节的亮度抽样比较和拷贝、生成假码流的填充字节、切片纠错），收齐并解码 0.26 ms，其余各项合计 0.25 ms。
最慢的是有丢包、码率高的会话（每秒包多，纠错是对真实字节算的）。

**但是导出时间线很慢**：每仿真一秒要 203 ms（画一遍像素，再按两种尺寸各转一次颜色），77 次会话一共 339 秒，是会话循环的一百多倍。
它是每种“画面内容”做一次的事，缓存只管同一进程里重复用同一份内容的情况；微软轨迹那组每个（轨迹，种子）的合成桌面种子都不同，所以每次都重新导出。
连导出一起算，现在的 L0 只有约 5 倍实时。

这说明两件事：
1. 控制逻辑本身跑到 500 倍没有问题，L0 的结构是对的。
2. **从像素导出的时间线只适合对账，不能当 L0 平时的画面来源。** 平时的来源应该是不经过像素的：操作模型直接生成内容描述，或者会话记录回放（A3、A4）。
   那时描述也不能再带 7 万字节的抽样（一条 720p、一分钟的时间线一两百 MB），要换成紧凑的形式（类别、面积、细节几个数，加一条“跳了帧时面积怎么累加”的规则），
   并且用现在这种“带抽样的精确描述”做基准来量它的误差。这一步放在 A3 开头做，在那之前批量跑 L0 可以先让同一份内容配多条网络（把合成桌面的种子和网络的种子分开），导出一次、用很多次。

**其他要知道的**
- L0 的阶段快照是一个黑点、信噪比是 NaN（没有像素）；报告里的截图对 L0 没有意义。
- 假后端的 `with_version_tag` 还留着：L0.5 是像素输入，版本号仍然靠它；L0 已经不用。
- 时间线只准备了原尺寸和半尺寸两种亮度抽样（现在的分辨率策略只有这两档）；以后分辨率档位变多、或者按控制端窗口缩放时，描述里要多带几份，否则编码器会报“没有这个编码尺寸的亮度抽样”。

## 11. S4 的结果（Sonnet，2026-11-27）

**做了什么**
- `peerdesk_core::kv`（`crates/core/src/kv.rs`，在 99% 覆盖率里）：通用的“一行一个键值”读写和内容哈希。读：键重复、没有值、键不合法、缺的键、值解析不了、
  没人认的键（`Kv::finish` 列出全部）都报带行号和键名的中文错误；写：键的顺序就是调用顺序，写不进文本的值（空、换行、两端有空白）报错。
  哈希是 blake3 的前 8 字节、16 位十六进制。值里的小字段写成 `名=值`，同一套规矩（`Kv::parse_fields`）。
- `peerdesk_e2e::world`（`crates/e2e/src/world.rs`）：`Scenario` 和世界文件互转（`to_text`、`from_text`）、`export`（按哈希命名写进目录，先写临时文件再改名，
  并行的测试写同一个场景不会互相截断）、`World::load`（文件名是 `<哈希>.world` 时核对内容的哈希）、`World::run`。
  `to_text` 里**解构** `Scenario` 和 `Link`：以后加字段，这里编译不过，逼着决定写不写进文件。
- `Scenario::fixed`：和 `Scenario::new` 同样的默认值，但一个环境变量也不读（L1 H.264、节奏器关、RS 纠错、起步探测开）；`new` 在它上面再叠环境变量，行为和以前一样。
  世界文件读出来的场景用 `fixed` 打底、每一项都由文件填。`trace`（调试输出）不写，读出来是关。
- `Scenario::byte_model`（`ByteModelKind::{Default, Openh264V1}`，世界文件的 `byte_model` 键）：`default` 是占位的 `DefaultByteModel`（默认，现有结果不变），
  `openh264-v1` 是 `FittedByteModel::openh264_v1()`（各类合在一起的系数，残差扰动开）。只对 `h264-l05`、`h264-l0` 有意义；别的编码配了非 `default` 的模型，读写都报错
  （否则同一个会话有两个哈希）。要加新模型（下一步的脏区域、移动区域输入），在 `ByteModelKind` 加一项和一个名字，文件格式不变。
- `PEERDESK_E2E_WORLDS=<目录>`：`run()` 每跑一个场景就把它的世界文件写进去（同一个场景重复跑只留一份）。不设时什么都不做。
- 批量运行器 `crates/e2e/examples/batch.rs`：`batch [--jobs N] [--out 文件.csv] <世界文件或目录>...`，每个会话一行 CSV，按输入顺序输出，出错的会话那行写原因、其余列空、退出码非 0。

**世界文件的键**（顺序固定）：`world`（格式版本 1）、`name`、`width`、`height`、`fps`、`codec`（tile、h264、h264-l05、h264-l0）、`byte_model`、`rng_layout`（1）、`seed`、
`estimator`（legacy、v1、gcc）、`profile`（stable、wireless、cellular、long-haul）、`policy`（office）、`start_bps`、`max_bps`、`pacing`、`fec`（rs、xor）、`start_probe`、`probe_ids`、
`phases N` 加 `phase.0 …`（`action=… frames=…`）、`links N` 加 `link.0 …`（`at`、`delay_us`、`jitter_us`、`fifo_jitter`、`batch_us`、`loss_permille`、`rate_bps`、`max_queue_us`、`up`、
`spikes`、`doze`、`busy`，一行一段，没有的写 `-`）。画像、策略写名字：没有命名的（自己造的 `Profile`、改过的 `ContentPolicy`）写不出来，报错。

**设计决定和理由**
1. **网络内联，不引用外部文件。** 微软轨迹每条几十到近 400 段（现有 99 个世界文件平均 10 KB、最大 62 KB（387 段））。引用外部文件要多一套“找不到、改过了没有、相对路径”的错误，
   世界文件就不再自包含：拷走一个文件就丢了网络，哈希也管不到被引用的内容。几十 KB 的文本不是问题，所以内联；哈希覆盖全部输入。
2. **线程，不用多进程。** 先查 `run()` 的全局状态：静态变量只有三处——RS 纠错的查表（`OnceLock`，进程内只初始化一次，之后只读）、节奏器倍数（`OnceLock`，读环境变量，只读）、
   操作时间线的缓存（有锁，只影响速度）；运行中不读别的环境变量（`PEERDESK_E2E_PROFILE` 只开计时）；openh264 没有进程级状态。`cargo test` 本来就在一个进程里并行跑几十个会话，
   指纹和单个跑的一致。线程省掉进程启动和结果回传。缺点：一个会话崩溃（panic）会带走整批；产品代码禁止 panic，可以接受。
3. **结果不受环境变量影响。** 世界文件把原来从环境变量取默认值的四项（编码种类、节奏器、纠错、起步探测）都写明，读出来用 `Scenario::fixed`。
   实测：设 `PEERDESK_E2E_CODEC=h264-l0 PEERDESK_FEC=xor PEERDESK_PACE=1 PEERDESK_START_PROBE=0 PEERDESK_EVENTS=1` 跑同一个世界文件，指纹和不设时相同。
   **唯一的例外**是节奏器倍数 `PEERDESK_PACE_FACTOR`（产品代码里的全局，只在节奏器打开时起作用）：世界文件不写它，运行时发现它被改了、而世界里节奏器是开的，
   就拒绝运行并说明原因（`world::env_conflict`），不静默用错。节奏器关着时它不起作用，照常跑。
4. **随机数布局号**写在文件里（`rng_layout 1`），读到别的号报错；A2 引入布局 2 时再放开。它是引擎的常量，不是 `Scenario` 的字段。
5. **文件名核对只在名字是 `<16 位十六进制>.world` 时做**（对不上说明文件被改过或拷坏了）；手写的世界文件用别的名字，不核对，内容照样逐项检查。
   哈希是文件字节的哈希，不是“解析后重新写出来”的哈希：手工改过格式（多空格、注释）的文件有自己的哈希。

**可疑的地方**
- `FittedByteModel` 的 `scene_key_permille` 是 850，假后端用的常量 `SCENE_PERMILLE` 是 900（`fake.rs`）。拟合文档说假后端应当取模型的数，现在没接；`openh264-v1` 模型下整屏突变的关键帧门槛因此和实测差 50‰。没改（不属于这一步，改了会动 L0/L0.5 的行为）。
