# M1：会话记录的格式和记录点（2026-11-27，设计，没有代码）

对应 `design.md` 1.8 节和第 8 节第 12 条：每次真实连接从连上到断开记一份记录，两端各一份；内测版自动上传，公开版要用户同意。
它是量尺的数据入口：孪生回放（L0 重放操作时间线、设备耗时、网络噪声）靠它，`P-fps-bitrate.md` 第 6 节缺的 8 类数据也一次补在这里。

## 1. 格式

### 1.1 为什么是自己的二进制格式

- 文本日志每秒一行不够重放，每帧一行又太大（一行 150 字节 × 每秒 60 帧 × 两类）。
- 现成的通用格式（protobuf 等）要加依赖和代码生成；我们的记录种类少、字段都是小整数，自己写一个“种类 + 长度 + 内容”的格式一两百行，
  核心库里已经有同样风格的读写器（`core::wire::{Reader, Writer}`、信令的“尾部可追加字段”规矩）。
- 可读性靠工具补：`peerdesk record dump`（见第 4 节 R8）把记录转成文本和每秒一行的表，代替现在的 `scripts/log-to-trace.py`。

### 1.2 文件结构

```
文件头：魔数 "PDSR" | 格式版本 u16 | 头长度 u16 | 元数据（TLV，见 1.4）
块 × N：块长度 u32 | CRC32 u32 | 块内容
        块内容 = 块的起始时间（微秒，绝对值）| 记录 × M
        记录   = 种类（变长整数）| 长度（变长整数）| 内容
```

- **可扩展**：读的一方遇到不认识的种类按长度跳过；认识的种类里多出来的尾部字段忽略（和信令一样）。加字段、加种类不用改版本号；
  版本号只在块结构变了时才加。
- **紧凑**：时间用“离上一条同类记录多少微秒”的变长整数；帧号、包序号用差值；多数字段 1–3 字节。
- **块**：每 1 秒或攒满 64 KB 封一块。每块自带起始时间，能单独解。CRC 用 `crc32fast`（已经在依赖树里）。
- **损坏和截断**：读的一方逐块校验，坏块跳过并计数，后面的块照常读；文件尾部不完整的那一块丢掉。
  正常结束时最后写一条“结束”记录（各类记录写了多少、丢了多少、会话怎么结束的）；没有它说明进程是崩掉或被杀的，这本身是一条信息。
- **写的过程中**文件名是 `.part`，正常结束后改名；启动时看到遗留的 `.part` 就原样保留并标成“未正常结束”，照样可以读、可以上传。
- 不在写的时候压缩（省 CPU、截断更好恢复）；上传时整体用 gzip（`flate2` 已经在依赖树里），估计能压到三分之一。

### 1.3 时钟

- 每条记录的时间是**本端的单调时钟**，从会话开始算的微秒。文件头里记一次会话开始时的墙上时间（Unix 微秒），只用来给人看和粗对。
- **两端对齐**不靠墙上时间（两台机器差几百毫秒到几秒都正常）。数据包头里本来就带发送端的发送时间，控制端每收一个包都能算
  `到达时间（本端单调）− 发送时间（对端单调）`。这一项的最小值 = 两端时钟差 + 最小单程延迟。控制端每秒记一条这个最小值（`时钟基准`记录）；
  被控端记往返时间。离线对齐：`时钟差 ≈ 基准 − 最小往返 ÷ 2`，误差不超过“最小往返的一半”（两个方向不对称时）。
  时钟漂移由每秒一条的基准序列自然覆盖。
- 帧号、探测组号两端一致，对账主要靠它们，时钟对齐只用于“延迟”这类跨端的量。

### 1.4 元数据（文件头，会话开始时写一次；能力变了再写一条“能力变更”记录）

| 字段 | 内容 | 来源 |
| --- | --- | --- |
| 会话号 | 16 字节。两端用同一个：从 QUIC 的 TLS 导出密钥材料取（标签 `peerdesk session record`）。不用改协议，也不能反推出设备身份 | `net/src/node.rs` 已经在用 `export_keying_material` 做通道绑定，同样的办法 |
| 角色 | 被控端 / 控制端 | – |
| 版本 | 程序版本、提交号、发行渠道（内测 / 公开）、格式版本 | `client/build.rs` 的 `PEERDESK_COMMIT`；net 包里现在拿不到，要由客户端传进会话选项 |
| 系统 | 系统种类和大版本 | `PeerOs::current()`、现有日志开头 |
| 路径 | 局域网直连 / 打洞直连 / 中继；IPv4 还是 IPv6。**不记地址** | `rendezvous` 选路的结果（现在日志里有“路径 Direct 局域网直连”） |
| 双方能力 | 握手里的能力位（两端的和共同的）；以后换成 C4 的能力描述 | `net/src/host.rs`、`controller.rs` 握手后的 `caps` |
| 编码 / 解码后端 | 名字、软件还是硬件；后端的属性表 | `BackendInfo`（C1）；`MediaReceiver::backend()` |
| 算法 | 估计器种类、内容策略、帧率设定、起步码率、码率上下限 | `SenderConfig`、`HostOptions` |
| 屏幕 | 原始尺寸、缩放比例、刷新率；控制端的显示区域 | `source.native_size()`、`platform::displays()`、“画面区域”流 |
| 设备 | 显卡厂商和型号、驱动版本；CPU 型号和核数；有线还是 Wi-Fi；电源模式 | **现在没有**，见 2.4 |

### 1.5 记录种类

被控端：

| 种类 | 什么时候记 | 字段（单位） |
| --- | --- | --- |
| 反馈 | 每处理一份反馈 | 时间；排队（微秒）、丢包（千分比）、送达（字节每秒）、确认到的帧号；延迟趋势（0.1 ms）、包串速率、探测结果（组号、速率、包数）；往返；在途字节；发送受谁限制（应用 / 网络加原因）；处理完之后的码率、码率状态 |
| 帧 | 每个编码任务结束 | 帧号；采集时间；类别（内容变化 / 补清晰 / 关键帧加原因）；变化面积（千分比，知道时）；预算（字节）；编出的字节（0 表示没出帧）；QP（知道时）；编码尺寸；各段耗时：缩放、转换、等待、计算、初始化（微秒）；后端丢帧的原因；是不是硬件 |
| 帧发完 | 一帧的最后一个分片交给 QUIC | 帧号、时间、分片数、纠错分片数 |
| 重传 | 每秒汇总 | 收到的请求片数、实际重传、因额度没传、判定丢帧数 |
| 没编的拍 | 每秒汇总 | 这一秒 60 拍里各原因的次数：画面没变、没到帧间隔、编码线程忙、在途满、节奏器忙、等关键帧确认、起步探测中 |
| 决定 | 发生时（带发生的时间，不是每秒取走的时间） | 种类代码 + 参数（码率从多少到多少、状态从哪到哪、帧率、分辨率、探测开始和结论）；现有的中文说明原文也带上（v1 先带，稳定后可以去掉省空间） |
| 采集 | 每秒 | 新画面数、读取次数、读取耗时合计和最大、出错重开次数 |
| 传输 | 每秒 | QUIC 的各项计数（交出、实际发出、挤掉、丢包、拥塞窗口、MTU） |
| 资源 | 每秒 | 进程 CPU 时间、编码线程 CPU 时间（**现在没有**，见 2.4） |
| 输入 | 每秒 | 收到的输入事件数，**只分三档**（0、1–5、更多）。不记按了什么键、鼠标在哪 |
| 换编码器 | 发生时 | 从哪个后端到哪个、原因 |

控制端：

| 种类 | 什么时候记 | 字段 |
| --- | --- | --- |
| 帧 | 每一帧有了定论 | 帧号；第一个分片到达时间、收齐时间；字节数；用了几个纠错分片；发过几次重传请求；结局（解码显示 / 作废 / 等关键帧跳过 / 解码失败）；解码开始时排在前面的帧数；解码耗时；交给界面的时间；**画到屏幕的时间**（见 2.3） |
| 时钟基准 | 每秒 | 1.3 节的最小值 |
| 显示 | 每秒 | 界面这一秒画了几次、其中几次是新画面、两次之间最长间隔、画一次的耗时 |
| 传输 | 每秒 | 同被控端 |
| 输入 | 每秒 | 发出的输入事件数（三档）；操作到画面的延迟（现有统计：次数、中位、最大） |
| 窗口 | 变化时 | 显示区域的尺寸、是否全屏、在哪块屏（序号）、刷新率 |

两端都有：开始、结束（原因、时长、各类记录的条数和丢弃数）、缺口（见 3.1）。

### 1.6 大小估计

按三份用户日志的节奏估（Mac 被控那份：平均每秒发 11 帧，画面在动时 20–30 帧，最高 48；决定每秒约 1.2 条；反馈在有包到的时候约每 20 ms 一份）：

| 记录 | 每条 | 平均每秒 | 最忙时每秒 |
| --- | --- | --- | --- |
| 反馈（被控端） | 约 14 字节 | 25 份 → 350 字节 | 50 份 → 700 字节 |
| 帧 + 帧发完（被控端） | 约 30 字节 | 11 帧 → 330 字节 | 60 帧 → 1.8 KB |
| 决定（带原文） | 约 120 字节 | 1.2 条 → 150 字节 | 降码率风暴时 10 条 → 1.2 KB |
| 每秒一条的五种 | 合计约 80 字节 | 80 字节 | 80 字节 |
| 块头、缺口等 | – | 约 10 字节 | – |
| **被控端合计** | | **约 0.9 KB/秒，3.3 MB/小时** | 约 4 KB/秒 |
| 帧（控制端） | 约 22 字节 | 11 帧 → 240 字节 | 60 帧 → 1.3 KB |
| 每秒一条的四种 | 合计约 50 字节 | 50 字节 | 50 字节 |
| **控制端合计** | | **约 0.3 KB/秒，1.1 MB/小时** | 约 1.4 KB/秒 |

两端合计每小时约 4.4 MB，gzip 后估计 1.5 MB 左右。这些是按字段宽度算出来的，不是量出来的；R3 做完后用仿真会话的真实记录核对，差得多就回头改这张表。

### 1.7 脱敏

不记：画面内容、键盘和鼠标的具体事件、剪贴板内容、文件名和路径、窗口标题、应用名、IP 地址和端口、设备码、证书指纹、账户号、电脑名、用户名。

记，但要知道它们的性质：
- 会话号：随机，只用来把两端的两份对上。在界面“关于这次会话”里显示前 8 位，用户要求删除时凭它找。
- 显卡型号、驱动版本、CPU 型号、屏幕尺寸：是硬件信息，不是个人信息，但组合起来能缩小到一类机器。内测版告知；公开版在同意上传的说明里列出。
- 输入只有每秒三档的活跃度。不记精确的击键时间：击键间隔能被用来猜输入内容。
- 路径只记类型，不记地址。服务端收上传时看得到来源地址，**不落盘**（只用于限速）。

脱敏规则公开写在仓库文档里；`peerdesk record dump` 让用户能看到自己机器上记了什么。

## 2. 记录点

原则：核心库（`crates/core`）不做读写，只把数据交出来；记录在会话循环（`crates/net`）里取，交给记录线程。能从现有接口拿到的不改核心库。

### 2.1 被控端（`crates/net/src/host.rs` 的 `serve` 循环）

| 记录 | 在哪取 | 怎么取 | 要改什么 |
| --- | --- | --- | --- |
| 反馈 | 处理控制通道数据报的分支：`media.on_feedback_datagram()` 之后 | `media.last_observation()`（反馈、扩展、往返、在途、受限原因）、`media.rate_bps()`、`media.rate_state()` | 不用改核心库。探测结果在反馈的扩展里（`ProbeReport`），`last_observation` 现在不带它，要加一个取最近探测报告的方法 |
| 帧 | 编码线程交回结果的分支（`encoded_rx.recv()`） | `job.frame_id`、`job.budget`、`job.scale_permille`；`took`、`timing`（`EncodeTiming`：缩放、转换、等待、编码、是否硬件、是否被丢、尺寸、关键帧原因）；编出的字节数；采集时间是定时器分支里的 `captured`，随任务一起传给编码线程再带回来 | `EncodeTiming` 加三项：QP（C1 的 `EncodedOut::qp` 已有）、变化面积（`H264Encoder::changed_permille` 的结果，显卡画面没有）、初始化耗时 |
| 类别 | 同上 | 交任务时的 `changed`；`EncodedFrame::key`；不变且出了帧就是补清晰 | 不用改 |
| 帧发完 | `send_paced()` 里每发出一个包之后 | `Outgoing::fragment` 带帧号和分片序号；分片总数在分片头里。一帧的最后一个数据分片发出时记 | `send_paced` 要知道“这是这一帧的最后一个”：让 `MediaSender::on_packet_sent` 返回“这一帧发完了”（它本来就在记每帧的发送历史） |
| 重传 | 每秒统计的分支 | `media.stats()` 前后两次的差（现有日志行就是这么算的） | 不用改 |
| 没编的拍 | 定时器分支：`encoding \|\| !media.frame_gate(...)` 那一行前后 | 画面没变、编码线程忙在循环里就知道；`frame_gate` 里的没到帧间隔、在途满、节奏器忙、等关键帧、起步探测现在只返回真假 | `MediaSender` 加 `gate_reason()`，返回最近一次 `frame_gate` 为什么不让编（纯逻辑，可单测）。循环里按秒累加 |
| 决定 | 每秒统计分支里的 `media.take_events()` | 现在取出来的是字符串，**时间是取的那一刻**（所以日志里同一秒的决定时间都一样） | `MediaSender::event()` 存成（时间，种类代码，参数，原文）；`take_events()` 保持不变给文字日志用，另加带时间的取法。种类代码先覆盖：码率状态切换、升降码率、帧率换档、分辨率、三种探测的开始和结论、显示区域变化 |
| 采集 | 每秒统计分支里的 `source.stats_line()` | 现在只有一行文字 | `ScreenSource` 加一个返回数字的方法；`platform/src/capture.rs` 已经有 `CaptureStats`（帧数、读取次数、耗时、重开次数），加上窗口内最大值即可 |
| 传输 | 每秒统计分支 | `link.quic_stats()`（`QuicStats`） | 不用改 |
| 换编码器 | 编码线程里 `encoder.backend()` 变了的地方 | 现在只更新名字 | 把原因带出来（`H264Encoder::soft_reason` 已有） |
| 输入 | 输入通道的分支 | `events.len()` 按秒累加再分档 | 不用改 |
| 元数据 | 握手完成之后、循环开始之前 | 见 1.4 | 提交号要从客户端传进 `HostOptions` |

### 2.2 控制端（`crates/net/src/controller.rs` 的会话循环）

| 记录 | 在哪取 | 怎么取 | 要改什么 |
| --- | --- | --- | --- |
| 帧：到达、收齐 | 视频数据报的分支：`MediaReceiver::on_datagram_deferred()` | 它返回收齐的帧（`DecodeJob`）；收齐用时现在只有每秒的平均和最大（`take_assembly_max`） | `DecodeJob`（或返回值）带上这一帧的第一个分片到达时间、字节数、用了几个纠错分片、请求过几次重传 |
| 帧：结局 | 同上，以及 `settle()` | 作废的帧号 `settle()` 已经返回；等关键帧跳过、解码失败在 `ReceiverStats` 里只有计数 | 让这两种也返回帧号 |
| 帧：解码 | 解码线程（`ReceiverDecoder::decode`）前后 | 现在按秒汇总进 `window.decode` | 每帧的耗时和“排在前面的帧数”（解码通道的长度）随结果带回 |
| 帧：交给界面 | `sink.present(&picture)` 前后（约第 470 行） | 已经在量（`window.present`），现成的 `frame_log.shown` 也在这里 | 不用改 |
| 时钟基准 | 视频数据报的分支 | 包头的发送时间和 `link.now()` 的差，按秒取最小 | `DelayTracker` 内部已经在算这一项（`interval_min`、`base`），加一个取原始最小值的方法 |
| 传输、输入、操作到画面 | 每秒统计的分支 | 现有两行统计的数字 | 不用改 |

### 2.3 画到屏幕（最难拿的一项）

“交给界面”不等于“画出来了”：`client/src/gui/session.rs` 的 `present()` 只是把画面放进一个槽，真正画是界面线程下一次重画时
（`gui/viewer.rs` 的 `show()`），拖动窗口、切全屏时界面线程可能停住（27b 那份日志怀疑的就是这个，当时没法证实）。

做法：记录线程的句柄做成可以克隆的发送端，会话启动时给界面一份。界面线程在 `show()` 里，发现槽里的帧号和上次画的不一样时记一条
（帧号，时间）；每秒再记一条“画了几次、最长间隔、画一次多久”。这量到的是“提交给显卡的时间”，不是“屏幕真的亮了”的时间（差一个垂直同步以内），
文档里写明这个定义。真正的上屏时间要系统的呈现统计，各平台不一样，不放进 v1。

| 4 读回分段、采集线程等待 | `EncodeTiming::wait_us`（fpsfix 第 1 步已有）是合计；分段（建纹理、拷贝、映射）在 `platform/src/wingpu.rs`，采集等待在 `capture.rs` 的采集线程 | 中：Windows 平台代码，本机只能做编译检查 |
| 5 CPU | 新增 `platform` 里的两个函数：进程 CPU 时间、当前线程 CPU 时间。Linux `clock_gettime`、macOS `thread_info`、Windows `GetProcessTimes` / `GetThreadTimes` | 中：三个平台各一份系统调用，要 `unsafe` 和平台 CI |
| 6 环境 | 提交号：已有，传进来即可。显卡型号和驱动：Windows 从 DXGI 适配器描述和驱动版本查询，macOS 从 Metal 设备名，Linux 的 `media/src/gpu.rs` 已有。刷新率：`platform::displays()` 要加一列。有线还是 Wi-Fi：Windows 看默认路由那块网卡的类型，macOS 看接口类型，Linux 看 `/sys/class/net/*/wireless`。电源模式：先不做 | **高**：平台接口多、本机验证不了，而且“默认路由走哪块网卡”在有 VPN 时会判错——判不出就记“不知道”，不猜 |
| 7 帧分两类 | 2.1 “类别” | 低 |
| 8 探测细节 | 每组包数、时长：`ProbeReport` 里已有包数，加时长；接收端一次读了几个包：`controller.rs` 读数据报的循环里按“同一次唤醒读到几个”计数，每秒记最大和平均 | 低 |

**最难拿的三项**：画到屏幕的时间（2.3，定义上只能到“提交给显卡”）；有线还是 Wi-Fi（VPN、多网卡时判不准）；硬件编码器内部的分段计时（各平台事件模型不同，
要随后端搬迁逐个做，而且本机跑不了）。这三项都不挡 v1：没有它们孪生回放照样能做，只是设备模型和类型标签粗一些。

## 3. 写盘和上传

### 3.1 写盘不拖慢会话

- 会话线程只做一件事：把一条定长的小结构（不分配内存）放进一个**有界队列**（约 8,000 条，按最忙时每秒 200 条算能扛 40 秒），放不进就不放，
  **永不阻塞**，同时给“这一类丢了几条”的计数加一。
- 记录线程从队列取、编码成块、写文件。每秒或每 64 KB 写一次，不调用同步刷盘（由系统决定什么时候落盘；断电丢最后几秒可以接受）。
- **不静默丢数据**：队列满过，下一个块开头写一条“缺口”记录（从什么时候到什么时候、各类各丢了几条）；“结束”记录里有总数。
  读的一方看到缺口就知道这一段不完整，孪生回放可以选择跳过这样的记录。会话的文字日志里也写一行。
- 写盘出错（磁盘满、没权限）：停止写这一份，计数继续，文字日志里写明原因和丢了多少；不重试、不影响会话。下一次会话重新尝试。
- 记录线程崩了不影响会话：队列的发送端发现对端没了就只计数。
- 仿真里（虚拟时间）不起线程，记录直接写进内存里的缓冲，保证确定性。

### 3.2 本机保留

- 目录：数据目录下的 `records/`，文件名 `<会话开始时间>-<会话号前 8 位>-<角色>.pdsr`。
- 保留最近 20 次或合计 200 MB，先到为准，从最旧的删；超过 24 小时的会话每满 24 小时切一个文件。
- 设置里可以关掉记录（关掉后不写任何文件）；“打开记录目录”“删除全部记录”各一个按钮。

### 3.3 上传

- **内测版**（发行渠道在编译时定）：会话正常结束后自动上传；首次启动时用一段话告知记了什么、不记什么、可以关。
- **公开版**：默认不上传。设置里有“帮助改进：上传会话记录”的开关，说明同上；另有“发送这次会话的诊断”的单次按钮。
- 通道：走到我们服务端的 QUIC 连接，新增一种流，和现有的崩溃报告上传（`StreamKind::Crash`、`service.rs` 的 `serve_crash`）同一个路数。
  先问服务器有没有这个功能（S0 的功能位加一位），老服务器不发。
- 内容：gzip 后的整份文件；带格式版本、会话号、角色、未压缩大小。单份上限 20 MB（约 4 小时的被控端记录压缩后的量），超过的截成多份。
- 失败重试：指数退避，最多保留 7 天；流量计费的网络上不传（判断不了就传，量很小）。上传成功后本机文件照保留策略留着，不立刻删。
- 用户要求删除：凭会话号前 8 位。

### 3.4 服务端

- 存放：数据目录下 `records/<日期>/<会话号>-<角色>.pdsr.gz`，另有一个索引文件（日期、会话号、角色、版本、大小、系统、后端），方便按版本和硬件挑。
- 限制：按来源地址限速（每小时若干份）、总量上限，超了拒收并让客户端晚点再试；来源地址不落盘。
- 保留：内测期 180 天；之后按产品负责人的决定。
- 成本粗估：内测 50 人、每人每天 2 小时 → 每天约 100 小时 × 1.5 MB ≈ 150 MB，180 天约 27 GB，现有服务器的磁盘放得下，流量可以忽略。
  公开后按 1,000 个同意上传的活跃用户算，每天约 3 GB，一年约 1 TB，放对象存储每月几十美元的量级；到那时改成抽样上传（例如每人每天一次，或只传有冻结、有降级的会话）。
- 部署在多节点时，记录只存在收到它的那个节点，由运维脚本定期汇总；不走节点间的状态同步。

## 5. 没验证、要诚实说的

- 大小是算出来的，没有量过；反馈在静止时到底多密、决定原文占多少，R3 之后才知道。
- 时钟对齐的误差上限是“最小往返的一半”，两个方向很不对称的链路（卫星、非对称宽带）上会偏；孪生回放用的主要是同一端内部的时间，受影响小。
- “画到屏幕”只能量到提交给显卡。
- 会话号从 TLS 导出：中继路径上两端各自和中继建连接的话，导出的值不一样。**这一点没有核实**（要看中继是转发整条 QUIC 连接还是两段连接）；
  如果是两段，会话号改成被控端生成、握手里带过去（要一个能力位）。R4 开始前先确认。
- 击键活跃度分三档够不够用于操作模型的校准，没有数据；不够也不放宽，改用画面变化的节奏来推断操作类型。
