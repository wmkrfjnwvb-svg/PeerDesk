# 音画同步和播放缓冲（电影模式的控制端部分）

> 调研日期：2026-11-26。**[已核实]** 表示这次读过原文（源码、规范或官方文档）；**[二手]** 表示来自讨论帖、论文摘要或搜索摘要，落地前要再确认。
> 代码：`crates/core/src/avsync.rs`（状态机）、`crates/net/src/controller.rs`（接进控制端）、`crates/e2e/src/avsync.rs`（仿真测量）。
> 测量：`cargo test --release -p peerdesk-e2e --test avsync -- --nocapture`。

## 0. 结论

1. **办公和看视频要的东西相反。** 办公要“收到就显示”；看视频要画面匀、口型对得上，多等一两百毫秒没人在意。
   WebRTC 的 `playout-delay` 扩展把这两种用法写得很直白：远程桌面、游戏用 0，电影用一个固定值。所以做成一个开关：
   播放延迟（毫秒），0 表示关。
2. **两端时钟不需要同步，只需要两路媒体用同一个被控端时钟打采集时刻。** 控制端取“到达 − 采集”的窗口最小值当时钟差
   （NetEQ 的相对到达延迟是同一个办法），画面和声音共用这一个时钟差，同一时刻采集的内容就在同一时刻播放。
   不需要 RTCP SR 那套 NTP 对时：WebRTC 要它是因为声音和画面是两条 RTP 流、时间戳各有各的起点和频率，我们自己定协议，直接带同一个时钟。
3. **目标：声音和画面的差落在 ±45 ms 之内。** ITU-R BT.1359-1 的可察觉门槛是声音早 45 ms、晚 125 ms；
   我们的声音一帧 10 ms、调整一次挪一帧，稳定后偏差不超过一帧，余量很大。
4. **播放延迟建议 150 ms 起步**（见 §3 的测量）：要装得下网络抖动 + 一帧分片发完的时间 + 丢包后重传一次的时间 + 编码解码用时。
   WebRTC 文档给的参考是互动流 100/150/200 ms、看视频约 400 ms；同行的远程桌面产品都没有公开的固定值。
5. **仿真里量到的效果**（§3）：抖动 30 ms 的链路上，显示间隔偏差 p95 从 18.1 ms 降到 0.0 ms；
   音画差从“声音晚 22–61 ms”变成固定的 3 ms。代价是画面延迟从 41 ms 变成 180 ms（播放延迟 150 ms 时）。

## 1. 别人怎么做

### 1.1 WebRTC

- **音画同步（`RtpStreamsSynchronizer` / `StreamSynchronization`）** [已核实，
  [stream_synchronization.cc](https://webrtc.googlesource.com/src/+/refs/heads/main/video/stream_synchronization.cc)]
  - 每条流用 RTCP SR 里的（NTP 时间，RTP 时间戳）对，把最新一个包的 RTP 时间戳换成发送端的 NTP 采集时刻。
  - 相对延迟 =（画面到达 − 声音到达）−（画面采集 − 声音采集）。正数表示画面落后。超出 ±10 秒就不管。
  - 相对延迟加上两路当前播放延迟的差，过 4 个样本的平均（`kFilterLength = 4`）；±30 ms 以内不动（`kMinDeltaMs = 30`）；
    否则取一半、每次最多改 80 ms（`kMaxChangeMs = 80`）。
  - 改法：谁落后，先减对方多加的延迟，没得减再给超前的那一路加延迟。结果写进声音的 NetEQ 最小延迟和画面抖动缓冲的最小播放延迟。
  - 也就是说：WebRTC 不让两路走同一条时间线，而是两个各自自适应的缓冲，再用一个慢速的反馈环把它们拉齐。
    好处是每一路都尽量低延迟；坏处是收敛慢（一次最多 80 ms），而且同步会反过来拖高延迟
    （讨论帖 [Chromium audio/video sync leads to unexpected latency](https://groups.google.com/g/discuss-webrtc/c/ZvAHvkHsb0E) [二手]）。
- **`playout-delay` RTP 头扩展** [已核实，
  [README](https://webrtc.googlesource.com/src/+/refs/heads/main/docs/native-code/rtp-hdrext/playout-delay/README.md)]
  - 定义：一帧从发送端采集到接收端显示的时间。发送端给出最小、最大值，各 12 位、单位 10 ms（0–40950 ms）。
  - 文档列的用法：远程桌面、游戏（没有声音时）最小 = 最大 = 0，接收端不做平滑、尽快显示；
    **电影播放最小 = 最大 = K，固定延迟，画面匀，声音也不用加速减速**；视频会议给一个范围让接收端自适应。
  - 参考值：互动流的上限 100、150、200 ms；看视频约 400 ms（最小值大一些，网络抖一下不至于卡住）。
- **画面抖动缓冲** [二手，`modules/video_coding/timing/timing.cc`]：显示时刻 = 按 RTP 时间戳外推的本地时刻 + 目标延迟，
  目标延迟 = max(最小播放延迟，抖动估计 + 解码用时 + 显示用时)。和我们这里的“采集时刻 + 时钟差 + 播放延迟”是同一个形状，
  区别是它的延迟自适应、我们的是配置值。

### 1.2 ITU-R BT.1359-1：多大的音画差看得出来

[已核实，[Rec. ITU-R BT.1359-1](https://www.itu.int/dms_pubrec/itu-r/rec/bt/R-REC-BT.1359-1-199811-I!!PDF-E.pdf)（1998，现行）]

| | 声音早于画面 | 声音晚于画面 |
|---|---|---|
| 可察觉 | 45 ms | 125 ms |
| 可接受 | 90 ms | 185 ms |

声音早比声音晚更容易看出来（现实里声音本来就比光慢，人习惯了声音稍晚）。所以拿不准时宁可让声音稍晚。

### 1.3 Moonlight / Sunshine

[已核实，Moonlight-Qt 的 [pacer.cpp](https://github.com/moonlight-stream/moonlight-qt/blob/master/app/streaming/video/ffmpeg-renderers/pacer/pacer.cpp)]

- “帧节奏”是按显示器的垂直同步出帧：解码好的帧进队列，每次垂直同步放一帧；队列最多 3 帧（`MAX_QUEUED_FRAMES`），
  多了丢最老的；平时目标是 1 帧，最近 500 ms 里队列空过才放宽到 3 帧。
- **没有音画同步**：不用显示时间戳排程，也没有声音时钟。声音走自己的缓冲。有人提过按帧数加播放缓冲的改动，
  作者自己说没把声音一起缓冲是个缺口（[moonlight-qt PR 1139](https://github.com/moonlight-stream/moonlight-qt/pull/1139) [二手]）。
- 游戏串流这样做说得通：延迟第一，几十毫秒的音画差玩游戏时不明显。看电影不行。

### 1.4 Parsec

[已核实，[高级配置项](https://support.parsec.app/hc/en-us/articles/360001562772-All-Advanced-Configuration-Options)]

- 画面收到就显示（可选垂直同步）。声音有一个客户端缓冲，配置项 `client_audio_min_buffer_ms = 50`、`client_audio_max_buffer_ms = 100`；
  声音断续时官方建议调大。
- 没有公开的音画同步机制，也没有画面的播放缓冲选项。

### 1.5 Chrome 远程桌面

- 走 WebRTC，主机发 `playout-delay` 0，接收端关掉平滑；早年的代码评审里还有“播放延迟大于 0 就让测试失败”的检查
  （[codereview 2887183004](https://codereview.chromium.org/2887183004) [二手，2017 年的代码，现在可能变了]）。
- 也就是说它只有办公这一种模式，看视频不是它的目标。

### 1.6 看视频时缓冲一般多大

- 点播、直播（HLS/DASH）缓冲以秒计，和这里不是一回事：它们不需要互动。
- 实时流：WebRTC 文档的参考值是 100–200 ms（互动）到约 400 ms（看视频）。
- 我们的场景介于两者之间：用户还要点暂停、拖进度条，延迟太大操作就发黏。150 ms 的播放延迟加上采集编码，
  点一下暂停到看见画面停大约 0.2 秒，和电视遥控器差不多。

## 2. 我们的设计

播放时刻 = 采集时刻（被控端时钟）+ 时钟差 + 播放延迟。画面和声音用同一个式子、同一个时钟差、同一个播放延迟。

- **采集时刻（被控端）**
  - 画面：帧头第二个字节加一个标志位（`FLAG_CAPTURE = 2`），帧头后面跟 8 字节采集时刻（会话时钟，微秒），每帧多 8 字节。
  - 声音：包里本来就有 `capture_us`，以前是“帧号 × 10 ms”，现在换成同一个会话时钟。
    声卡一次交来几帧时“交来的时刻”有抖动，所以时间线仍按帧号等间隔走，只在偏离超过 5 ms 时挪一次起点（`CaptureClock`）。
- **兼容**：新能力位 `Caps::AV_SYNC`（第 27 位）。双方都有才带采集时刻；老的控制端不认带标志位的帧头（会当坏帧），所以对老版本不带。
  老的被控端不带采集时刻，新的控制端收到没有采集时刻的帧就马上显示，和现在一样。
  控制端只有在这次会话给了播放延迟这个设置时才声明这个能力位（没给就从握手里去掉），所以现在的客户端线上字节和以前完全一样。
- **时钟差（控制端，`ClockMap`）**：最近 10 秒里“到达 − 采集”的最小值。
  最小值是走得最快的那个包，抖动只会让别的包更晚；窗口让它跟得上时钟漂移和路径变化。
  **有声音时只按声音包算，没有声音时才按画面帧算。** 一开始两路混在一起取最小值，量出来有问题：
  - What：Wi-Fi 链路上显示间隔偏差平均是 0，但最大有 9.4 ms，同时音画差有一段是 −9 ms。
  - Why：画面帧有大有小。码率爬上去之后一帧 80 KB，在 50 Mbps 的链路上光发完就要 13 ms，“到达 − 采集”是 20 ms；
    开头码率低时的小帧只要 3.7 ms。时钟差一直是那个小帧定的 3.7 ms，10 秒后它出了窗口，时钟差跳到声音包定的 13.05 ms。
  - How：声音包每个一样大、间隔一样，拿它当基准。改完同一条链路上最大偏差 9.4 → 0.0 ms，音画差固定在 0。
- **画面（`FrameQueue`）**：解码好的帧按播放时刻排队，到时间才显示。不改顺序、不丢帧；
  到的时候已经过了播放时刻的帧马上显示并计数（“迟到”）；压了超过 64 帧就不再等。
- **声音（`JitterBuffer::pop_synced`）**：打开时播放时刻不由水位定，而由采集时刻定。离时间线一帧以内正常播；
  早了多播一帧补偿（减速），晚了两帧压成一帧（加速）；差得多（超过 60 ms，刚打开或改了播放延迟时）直接等或者跳过去。
- **开关**：`ControllerOptions::playout_ms`（`None` 或 0 表示关，可以在会话中途改）。关着时不建同步对象，
  画面收到就显示、声音走水位，和以前的代码路径一样。

和 WebRTC 的区别：它是两个各自自适应的缓冲加一个反馈环；我们打开时是一条固定的时间线，没有环，所以没有收敛过程，
音画差由构造保证（声音一帧的量化 + 画面定时器的精度）。代价是延迟不自适应：播放延迟装不下的抖动会表现为画面迟到、声音补偿。
这是电影模式要的取舍；自适应的播放延迟（按迟到率调）留到以后。

## 3. 仿真测量

办法：`crates/e2e/src/avsync.rs`。产品的发送端、接收端、真实的 H.264 编码器（720p、30 帧），画面是桌面上放视频；
另加一路声音（每 10 ms 一个包，120 字节，等于 96 kbps 的 Opus），和画面走同一条仿真链路。控制端和产品的会话循环一样接。
每次放 20 秒，开头 3 秒不算。仿真是确定性的，同一个种子结果一样。

- **显示间隔偏差** = 相邻两帧的显示间隔 − 它们的采集间隔（绝对值）。0 表示节奏原样重现。
- **音画差** = 画面延迟 − 声音延迟。正数是声音早于画面（可察觉门槛 +45 / −125 ms）。
- **迟到帧**：到的时候已经过了播放时刻（马上显示）。

怎么读：

- **关着时**画面收到就显示，显示间隔跟着网络抖动走（抖动 30 ms 的链路上 p95 偏 18 ms，一帧才 33 ms）。
  声音走自己的抖动缓冲，比画面晚 30–60 ms，还在不停地加速减速（89 次 / 90 次）去追水位。
  这个差在可察觉门槛（声音晚 125 ms）之内，所以办公时没人抱怨；但它不是固定的，会跟着抖动漂。
- **打开后**不丢包的链路上显示间隔原样重现（偏差 0.1 ms 以内），音画差固定在 0–3 ms，声音不再加速减速。
  剩下的 3 ms 是控制端声音节拍和时间线之间的相位（节拍 10 ms 一次，落在哪就是哪，上限一帧）。
- **画面延迟 = 播放延迟 + 最快的声音包从采集到到达的时间**（声音一帧 10 ms 录完才发，再加网络的最短延迟）。
  Wi-Fi 上是 150 + 13 = 163 ms。
- **有丢包时播放延迟要装得下一次重传**：蜂窝链路往返 80 ms 以上，丢了分片的帧要等重传。
  50 ms 装不下（28 帧迟到，15 帧音画差能察觉）；150 ms 剩 6 帧迟到、最大差 14 ms，察觉不到；250 ms 全部装下。
  声音的 33 次补偿是丢了的包（这个仿真没开声音冗余；产品里丢包超过 0.5% 会带上前一帧的副本）。
- 播放延迟太小不会更糟：迟到的帧马上显示，退化成关着时的样子。

仿真没有的：解码用时（仿真里解码不占时间；产品里每帧几毫秒，等于播放延迟少了这几毫秒的余量）、
声卡的输出延迟、显示器的刷新时刻、两端时钟的漂移（单元测试里有）。

**关着时不变**：`e2e` 里的 `office_on_lan`、`office_on_cellular`、`video_on_a_narrow_link`、`random_loss_without_congestion`
四个场景，改动前后的输出（表格、门槛、JSON、截图）逐字节相同。
对照：如果被控端每帧都带采集时刻（8 字节），这四个场景仍然全部达标，但数字不再逐字节相同（例如蜂窝办公场景最长等待 520 → 369 ms，
仿真里随机丢包落在哪个包上跟着字节数变，不是变好了）。所以采集时刻只在控制端声明了能力位时才带。

**顺带发现（不在这次范围内）**：抖动 30 ms、带宽 20 Mbps、不丢包的链路上，码率估计把抖动当成拥塞，码率掉到 149 kbps，
发送端只发出约 10 帧每秒（20 秒里 510 帧只编了 218 帧）。看电影时这比音画同步更要命，电影模式的策略要处理。

## 4. 没做的

- 播放延迟不自适应（见上）。迟到帧数有计数，以后可以据此调，也可以在工具条提示。
- 没有按显示器的垂直同步出帧（Moonlight 的做法）。播放时刻和刷新时刻不对齐时，还有最多一个刷新周期的量化。
- 声音的调整是整帧的（10 ms），没有时间伸缩（WSOLA）。稳定后不调整，所以听不出来；播放延迟改变的瞬间会有一次。
- 声卡输出延迟（系统混音器、蓝牙耳机）没有算进去。蓝牙耳机常见 150–250 ms，会让声音晚于画面，方向上是比较不容易察觉的那一边，
  但超过 125 ms 还是看得出来。要解决需要从系统接口读输出延迟，再把画面相应推后。
- 被控端只在握手时决定带不带采集时刻（控制端声明了就带），每帧多 8 字节（30 帧时 1.9 kbps）。
  控制端给了播放延迟设置但设成 0 时也带着。要做到“切到电影模式才带”，需要模式切换消息通知被控端
  （`MediaSender::set_capture_stamps` 可以中途开关）。
- 没有声音的会话只能按画面帧算时钟差，大帧小帧进出窗口时时钟差会跳（上面量到 9.4 ms）。没有声音时不存在音画差，
  只表现为一次显示间隔的偏差。
