# 剪贴板同步设计

范围：第一期只做**文本和图片**，双向。复制文件后右键粘贴（文件剪贴板）放到第二期，第一期复制了文件时提示用户走文件传输。

## 1. 业界做法

- **RDP**：先只发“格式列表”，对方真的粘贴时再请求内容（延迟渲染）。好处是大内容不粘贴就不传；
  代价是要在每个系统上实现延迟渲染（Windows `WM_RENDERFORMAT`、macOS `NSPasteboardItemDataProvider`、
  X11 选择区请求），而且粘贴时要等网络，粘贴大图会卡住对方的程序。
- **Parsec / AnyDesk / ToDesk**：复制时直接把内容推过去，有大小上限。实现简单，粘贴不用等网络。

**我们的选择**：复制时直接推送（和 Parsec 一致），设大小上限；超过上限不推，提示用文件传输。
以后做文件剪贴板时，小文件同样直接推，大文件再考虑延迟渲染。

## 2. 协议

- 能力位 `Caps::CLIPBOARD`，两端都支持才开启；老版本对端不支持时界面置灰（见 `docs/compat.md`）。
- 一条专用的可靠 QUIC 流（新的流类型），由控制端在会话建立后打开，双向复用。它和视频、输入分开：
  传大图时不挡输入和画面。
- 消息：
  - `Offer { seq, kind: Text | Png, size }`，然后分块发内容（每块 64 KB），最后 `Done { seq, hash }`。
  - 新的复制开始时，未发完的旧内容作废（`seq` 更大的覆盖），只同步最新的一份。
  - `TooLarge { kind, size }`：内容超过上限，只通知对方，界面提示。
- 图片统一用 PNG（无损、各系统都认），被控端截图 4K 大约 2–6 MB。

## 3. 大小上限（可配置，默认值）

| 内容 | 上限 | 超过时 |
|---|---|---|
| 文本 | 4 MB（约 200 万汉字） | 不同步，提示 |
| 图片（PNG 编码后） | 16 MB | 不同步，提示“图片过大，请用文件传输” |
| 文件 | 第一期不同步 | 提示“复制的文件请拖到远程窗口，或用文件传输” |

## 4. 什么时候同步

- **控制端 → 被控端**：远程窗口在前台时，本机剪贴板一变就推送；切回远程窗口时补推一次最新内容。
- **被控端 → 控制端**：被控端剪贴板一变就推送。
- **防回声**：写入本机剪贴板的远端内容记下哈希，下次读到相同内容不再推回去。
- **检测变化**：Windows 用剪贴板序号（`GetClipboardSequenceNumber`），macOS 用 `changeCount`，
  X11 用 XFixes 选择区通知。都是只读一个计数，开销可以忽略，不轮询内容本身。

## 5. 安全和隐私

- 被控端的权限开关里加“剪贴板”，和文件传输一样可以关；控制端远程窗口里也可以单独关掉。
- 跳过密码管理器标记为敏感的内容（Windows `ExcludeClipboardContentFromMonitorProcessing`、
  macOS `org.nspasteboard.ConcealedType`）。
- 日志里只记大小和耗时，不记内容。

## 6. 测试和指标

- 单元测试：分块、作废旧内容、超限通知、防回声、哈希校验。
- 端到端：两端真实会话，内存里的假剪贴板（测试构建不碰开发者电脑的剪贴板）：
  - 复制文本到对方可粘贴的延迟，门槛 300 ms（局域网）；
  - 4K 截图（约 5 MB PNG）在 50 Mbps 链路上 2 秒内到达，期间输入延迟不受影响；
  - 老版本对端（没有剪贴板能力位）：会话正常，剪贴板关闭。
- 真实系统剪贴板的胶水代码（读写、变化检测）放在平台层的系统接口文件里，在 CI 的各平台实机测试里验证。
